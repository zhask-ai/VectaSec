## KQ1. The full posture checklist per gateway / mesh / ingress

### Takeaway
Authoritative hardening guidance converges on the same ~12 control families across every gateway and mesh (admin-plane exposure, per-route auth with no anonymous fallback, TLS in/out, JWT/JWKS hygiene, rate/size limits, CORS, logging/audit, WAF, secrets-out-of-config, RBAC/workspace scoping, version/CVE/EOL, config drift). What differs per product is the config key, the read-only evidence endpoint, and the specific 2023-2026 CVE that makes each control non-theoretical — those are enumerated below.

### Cited Findings

**Cross-product frameworks (what every check should map to)**
- OWASP API Security Top 10 (2023): API1 BOLA, API2 Broken Authentication, API3 Broken Object Property Level Authorization, API4 Unrestricted Resource Consumption, API5 Broken Function Level Authorization, API6 Unrestricted Access to Sensitive Business Flows, API7 SSRF, API8 Security Misconfiguration, API9 Improper Inventory Management ("unknown hosts or versions leave deprecated APIs and debug endpoints exposed"), API10 Unsafe Consumption of APIs — [OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10/)
- Gateway-config checks map most naturally to API2 (auth plugins per route), API4 (rate/size limits), API7 (jwksUri / upstream URL SSRF), API8 (misconfiguration generally) and API9 (inventory, zombie routes, debug/admin endpoints) — inference from the list above.

**Kong (OSS / Enterprise / Konnect)**
- Kong's own Admin API hardening page: keep `admin_listen` minimal (default `127.0.0.1:8001`), "avoid using values such as `0.0.0.0:8001`"; bind to a private interface if needed; host firewall (iptables) allow-list on 8001; optional "API loopback" pattern (Service -> `http://127.0.0.1:8001`, Route `/admin-api`, `key-auth` + `ip-restriction`/`acl` plugins); custom Nginx `server`/`location` blocks with native auth; Enterprise RBAC for Admin API resources. The page does not cover `admin_gui` or TLS on the admin listener — [Kong: Secure the Admin API](https://developer.konghq.com/gateway/secure-the-admin-api/)
- Third-party (Invicti vuln DB) guidance for an exposed Kong Admin API: bind to localhost, firewall allow-lists, SSH/VPN for remote admin, monitor Admin API access logs; OSS has no built-in admin auth, so a reverse proxy with auth is needed — [Invicti: Unprotected Kong Gateway Admin API](https://www.invicti.com/web-application-vulnerabilities/unprotected-kong-gateway-admin-api-interface)
- Kong's Konnect hardening webinar is summarized as a 24-point checklist across network security, secrets management, authentication, observability, resilience. Named controls: disable plain HTTP on gateway listeners; admin endpoints reachable only via approved encrypted paths; DB passwords/tokens out of config files, use vault integrations; scope RBAC for admin functions; explicit access boundaries on admin routes; rate-limit admin routes; enable audit logs, admin-command visibility and change evidence. Full 24 items not public in the article — [NHI Mgmt Group summary of Kong webinar](https://nhimg.org/articles/konnect-hardening-checklists-show-where-api-gateway-risk-starts/)
- key-auth plugin: `config.key_in_query` is enabled by default and Kong itself warns query-string keys "can appear in application logs and browser URL bars"; `config.key_in_header` is the recommended option; when auth fails and an anonymous Consumer is configured the plugin sets `X-Anonymous-Consumer: true` upstream; credentials managed via `/consumers/{usernameOrId}/key-auth`; Konnect principals via `/v2/directories/{directoryId}/principals/{principalId}/api-keys` — [Kong key-auth plugin](https://developer.konghq.com/plugins/key-auth/)
- Auth plugins must be scoped to a Route, Service, or globally — never to a Consumer; centrally-managed Konnect consumers support only key-auth — [Kong Consumer entity](https://developer.konghq.com/gateway/entities/consumer/)
- Kong CVEs 2026: CVE-2026-6338 HTTP request smuggling/desync in Kong Gateway Enterprise 3.4, 3.10-3.14 series (published 2026-06-11; fix version not on the CERT-HR page) — [CERT.hr CVE-2026-6338](https://cve.cert.hr/cve/CVE-2026-6338); CVE-2026-14917 SAML plugin auth bypass only when `validate_assertion_signature` (default on) was disabled, fixed in 3.15.0 — [SentinelOne CVE-2026-14917](https://www.sentinelone.com/vulnerability-database/cve-2026-14917/); CVE-2026-15228 (KIC 3.4.x/3.5.x) and CVE-2026-16543 (Kong Operator / embedded KIC, CVSS 4.0 7.1, GHSA-h4fh-j7xg-vwcx) — a CA-certificate ID collision by any user with namespace-scoped Secret create rights halts config updates cluster-wide — [cvefeed CVE-2026-16543](https://cvefeed.io/vuln/detail/CVE-2026-16543), [cvefeed CVE-2026-15228](https://cvefeed.io/vuln/detail/CVE-2026-15228); older CVE-2021-27306 JWT plugin let unauthenticated users reach protected routes before 2.3.2.0 — [cve.yack.one konghq](https://cve.yack.one/vendors/konghq)

**Istio (sidecar and ambient)**
- Official best practices with config keys: mTLS default is PERMISSIVE, "migrate to strict mode"; mTLS authenticates but does not authorize — pair with `AuthorizationPolicy`; start from an `allow-nothing` default-deny policy; for ambient waypoints (1.25+) bind an AuthorizationPolicy to the `istio-waypoint` GatewayClass via `targetRefs` in the root namespace (`istio-system`) and keep the classic default-deny since ztunnel enforces it; ALLOW policies should use only positive fields (`paths`, `values`), DENY only negative fields (`notPaths`, `notValues`); `meshConfig.pathNormalization.normalization` ∈ `NONE|BASE(default)|MERGE_SLASHES|DECODE_AND_MERGE_SLASHES`; authz is inbound-only and server-first TCP protocols leak initial bytes; capture is TCP-only, port 22 and `excludeInboundPorts`/`excludeOutboundPorts` bypass it; apps can remove their own sidecar so layer NetworkPolicy; `outboundTrafficPolicy: REGISTRY_ONLY` "isn't a security control"; DestinationRule TLS origination needs both `tls.caCertificates` and `tls.subjectAltNames` (+ `tls.sni`); Gateway: restrict creation via RBAC/OPA, avoid `hosts: ["*"]`, dedicated gateway for sensitive domains, mixed mTLS/simple-TLS under wildcard SNI needs a 421-abort VirtualService because Envoy doesn't enforce Host/SNI match; exact host matches don't cover ports (`example.com`, `example.com:*`); `hosts`/`notHosts` are ignored on sidecars; declare protocols explicitly; use Istio CNI (no `NET_ADMIN`/`NET_RAW`); distroless images; TOC also lists locking down control-plane/data-plane ports, third-party SA tokens, downstream connection limits — [Istio Security Best Practices](https://istio.io/latest/docs/ops/best-practices/security/)

### Inferences
- A single normalized rule schema works across all products: {admin-plane-reachable, listener-plaintext, route-without-auth, auth-anonymous-fallback, jwt-weak-validation, jwks-unrestricted, upstream-tls-unverified, rate-limit-missing, body-size-unbounded, cors-wildcard-with-credentials, logging-off, waf-absent, secret-in-config, rbac-overbroad, version-eol/cve, declared-vs-live-drift}. Every vendor baseline above (Security Hub, Defender, Kong checklist, Istio BP) is a subset of this.
- The highest-value 2025-2026 lesson is **fail-open on dependency failure**: Istio JWKS-fetch-failure => default keys (CVE-2026-31837), Envoy `failure_mode_allow` on ext_authz, Istio BackendTLSPolicy fail-open on sidecars (2026-006), Envoy `safe_regex` fail-open. A posture tool should flag every config where the auth/TLS dependency failure path is "allow" (ext_authz `failure_mode_allow: true`, Kong/APIM caching of JWKS without `BLOCKED_CIDRS_IN_JWKS_URIS`, missing `IST0175`).
- Second recurring class is **namespace-boundary confusion in Gateway API implementations** (Traefik CVE-2026-54761/54765/65601, Kong KIC CA-ID collision, ingress-nginx admission RCE). A check "which namespaces/tenants can influence this listener" (AllowedRoutes + ReferenceGrant + Secret-create RBAC + crossProviderNamespaces) is a differentiated, config-derivable graph query.
- Third class is **regex/matcher semantics**: Istio `serviceAccounts` dots-as-regex, Envoy header-concatenation RBAC bypass, path-parameter canonicalization. A check that lints AuthorizationPolicy / RBAC matchers for unescaped regex metacharacters and multi-valued-header matches is cheap and currently absent from istioctl.
- Prior-knowledge (unverified this session) config keys worth checking: Kong `config.anonymous` on every auth plugin (when set, failed auth falls through to the anonymous consumer; with multiple auth plugins it becomes logical-OR), `admin_gui_listen`, `ssl_cipher_suite`, `trusted_ips`/`real_ip_header`, `declarative_config` vs DB mode (`database=off`) for drift, `kong.conf` `vaults`; Tyk `secret`/`node_secret`, `hash_keys`, `use_keyless`, `enable_jwt`, `jwt_signing_method`, `strip_auth_data`, dashboard `/api/apis`; Gravitee `plan.security` (KEY_LESS plan = anonymous), `/management/v2/apis`; KrakenD `endpoint.extra_config` with `auth/validator`, `security/cors`, `router.return_error_msg`; HAProxy `stats` socket/`stats uri` exposure; NGINX Plus `api` module write mode; Zuplo policies. Treat as hypotheses to validate against vendor docs.

## KQ2. What "API posture management" vendors do that a config-reading tool cannot, and vice versa

### Takeaway
Traffic-based APSM vendors (Salt, Akamai/Noname, Traceable/Harness, Akto, Defender for APIs, Cloudflare API Shield) uniquely see shadow/zombie endpoints, spec-vs-runtime drift and sensitive data in payloads; spec-based tools (42Crunch) uniquely score the contract. A config-reading tool uniquely sees the *control plane*: admin-plane exposure, fail-open settings, anonymous fallbacks, cross-namespace trust, key hygiene and drift between declared and live config — none of which are visible in traffic or specs.

### Cited Findings
- Defender for APIs' "unused endpoint" rule is defined purely from traffic (no traffic for 30 days) and its "should be authenticated" rule is evaluated by observing whether `validate-jwt` / `validate-client-certificate` / `validate-azure-ad-token` policies execute or subscription keys are present at call time — i.e., effective policy inferred from runtime, not from config — [Defender for Cloud API recommendations](https://learn.microsoft.com/en-us/azure/defender-for-cloud/recommendations-reference-api)
- Cloudflare API Shield builds schema profiles either from uploaded OpenAPI or from traffic ("Schema Learning") and does endpoint discovery, volumetric abuse detection and sequence analytics — all traffic-side — [Cloudflare API Shield](https://developers.cloudflare.com/api-shield/)
- Salt (vendor-claimed): Salt Collect analyzes live traffic; "Eliminate shadow APIs"; surfaces shadow MCP servers; flags PII moving into/out of LLM calls; detects "posture drift"; integrates with Kong, AWS API Gateway, Apigee, MuleSoft, NGINX, F5, Akamai, Cloudflare, Fastly, Istio (as traffic sources) — [Salt platform page](https://salt.security/platform); Salt also pushes posture gaps and live attacks into Wiz — [Salt + Wiz blog](https://salt.security/blog/strengthening-cloud-security-api-posture-governance-threat-detection-and-attack-chain-visibility-with-salt-security-and-wiz)
- Akamai acquired Noname (~$450M, mid-2024) and lists four domains: discovery, posture management, runtime protection, active testing; Traceable merged with Harness March 2025; 42Crunch treats the OpenAPI spec as single source of truth; Akto claims 1,000+ built-in tests mapped to OWASP API Top 10 with CI/CD plus runtime posture (vendor-claimed roundups) — [AppSecSanta tool roundup](https://appsecsanta.com/api-security-tools), [Akto vs 42Crunch (vendor)](https://www.akto.io/resources/akto-vs-42crunch)
- Wiz API SPM (vendor-claimed): discovers APIs, checks exploitability, ranks fixes; maps Apigee gateways and Akamai edge configs onto the Security Graph; FireTail integration adds traffic monitoring correlated to attack paths — [Wiz author page](https://www.wiz.io/it-it/authors/gilad-hoze), [Wiz FireTail integration](https://www.wiz.io/fr-fr/integrations/firetail)
- Orca (vendor-claimed): agentless multi-cloud API discovery, argues WAFs and gateways give partial coverage; has config-level checks such as API Gateway without WAF — [Orca multi-cloud API security](https://orca.security/resources/blog/multi-cloud-api-security-visibility-and-risk-management/)
- GraphQL hardening that is only verifiable from config/code, not traffic: introspection disabled, GraphiQL disabled, field suggestions off, max query depth (`MaxQueryDepthInstrumentation`, `graphql-depth-limit`), cost analysis (`MaxQueryComplexityInstrumentation`, `graphql-cost-analysis`), batch-operation caps, batching disabled for passwords/OTP/tokens, resolver-level authz on edges *and* nodes, removal of unneeded `node`/`nodes` root fields; "even if introspection is disabled, attackers can still guess fields" — [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html)
- Istio's own warning that an app can remove or bypass its sidecar and that port 22 / excluded ports are not captured means traffic-based mesh observability is itself incomplete without config/NetworkPolicy review — [Istio Security Best Practices](https://istio.io/latest/docs/ops/best-practices/security/)

### Inferences
- Config-only is strictly better at: admin-plane reachability (Kong `admin_listen`, Traefik `api.insecure`, APIM direct-management endpoint, Envoy admin `/stats`, istiod 15010/15014), fail-open flags, anonymous consumers, cross-namespace trust graphs, secrets-in-config, declared-vs-live drift (decK/Konnect vs Admin API; Istio CRDs vs `config_dump`), version/EOL. Traffic tools cannot see any of these.
- Traffic-only is strictly better at: zombie/unused endpoints (30-day no-traffic), undocumented (shadow) endpoints not present in any gateway route, spec-vs-runtime response drift, PII/secrets in payloads, BOLA/business-flow abuse. A config tool can approximate "zombie" via gateway access logs / Konnect analytics / CloudWatch metrics (`Count` per route = 0) but not "shadow" unless it compares gateway routes against a discovered app surface (EASM, k8s Services without a Route).
- The buyer-visible seam is **effective-auth per route**: Defender derives it from traffic, a config tool derives it from plugin/policy composition. A product that does both (config-derived expectation vs traffic-observed enforcement) catches the Kong anonymous-fallback and Envoy fail-open classes that neither side catches alone.
- Prior knowledge (unverified this session): 42Crunch Audit scores a spec 0-100 across Security / Data Validation / OpenAPI-format categories with named issue ids; Akto has traffic connectors for Kong, AWS API GW, Envoy/Istio mirroring and an "AI agent skill governance" 2026 release (the Akto page title in results mentions "AI Agent Skill Governance, Guardrail Remediation"). Both should be verified before being cited as fact.

- 42Crunch rule catalogue and scoring page returned 404; Akto docs path returned 404; Wiz API-SPM blog URL not confirmed.

## KQ3. What an AI/LLM gateway posture check looks like

### Takeaway

## KQ4. What buyers expect beyond checks: route-to-identity map, effective-policy computation, mesh authorization graph, zero-trust scoring

### Takeaway
The vendor and OSS ecosystems supply the raw read-only inputs (Kong Admin API, Traefik `/api/rawdata`, Istio `config_dump` and debug endpoints, Linkerd audit metrics, Hubble policy verdicts, Bifrost/LiteLLM governance APIs) but none of the surveyed sources offers a product that computes "what actually applies to this request" across plugins/policies or a cross-mesh authorization graph; Linkerd explicitly has no effective-policy command, istioctl only lints, and Defender infers effective auth from traffic. This is the open space.

### Cited Findings
- Linkerd docs offer no command for viewing effective policy; only indirect signals (Server accessPolicy default deny, `authz_name=audit` metrics, 403/refused) — [Linkerd server policy](https://linkerd.io/2/features/server-policy/)
- Cilium exposes per-endpoint enforcement state (`cilium-dbg endpoint list`) and per-flow verdicts (`hubble observe flows -t policy-verdict`) but the fetched pages describe no "effective policy for pair (A,B)" query — [Cilium policy creation](https://docs.cilium.io/en/stable/security/policy-creation/)
- istioctl analyze checks "known best practices and common mistakes" (schema, references, routing) and has no analyzer for over-broad ALLOW or PERMISSIVE mTLS; third parties add those as separate guardrails — [Istio analysis reference](https://istio.io/latest/docs/reference/config/analysis/), [Earthly Lunar Istio guardrails](https://earthly.dev/lunar/guardrails/istio/)
- Istio's own best-practices page enumerates the composition pitfalls an effective-policy engine must model: ALLOW positive-only / DENY negative-only, `hosts` ignored on sidecars, port-less exact host matches, path normalization order (percent-decode -> RFC 3986 -> merge slashes), inbound-only authz, excluded ports, waypoint vs ztunnel enforcement in ambient — [Istio Security Best Practices](https://istio.io/latest/docs/ops/best-practices/security/)
- Istio debug surfaces that an authorization-graph builder can read (and which must themselves be posture-checked): istiod XDS port 15010 (previously unauthenticated `config_dump`), HTTP debug endpoints on 15014 (now namespace-authorized) — [ISTIO-SECURITY-2026-001](https://istio.io/latest/news/security/istio-security-2026-001/); Snowcat already consumes `--discovery-address` and `--debugz-address` for its audit — [praetorian-inc/snowcat](https://github.com/praetorian-inc/snowcat)
- Traefik `/api/rawdata` returns "dynamic configurations, errors, status, and dependency relations" — a ready-made route->middleware->service graph source — [Traefik API reference](https://doc.traefik.io/traefik/reference/install-configuration/api-dashboard/)
- Defender for APIs derives "endpoint is authenticated" from observed execution of `validate-jwt`/`validate-client-certificate`/`validate-azure-ad-token` or subscription-key presence — i.e., Microsoft's effective-auth model is traffic-observed, not config-computed — [Defender API recommendations](https://learn.microsoft.com/en-us/azure/defender-for-cloud/recommendations-reference-api)
- Gateway API security model expects a four-persona RBAC split and recommends ValidatingAdmissionPolicy for hostnames, ReferenceGrants and GatewayClass use — the trust inputs for a "who can influence this listener" graph — [Gateway API security model](https://gateway-api.sigs.k8s.io/concepts/security-model/)
- Kong Konnect checklist explicitly lists "admin command visibility and change evidence" (audit trail of administrative actions) as a control — [NHI Mgmt Group summary](https://nhimg.org/articles/konnect-hardening-checklists-show-where-api-gateway-risk-starts/)
- Bifrost exposes `/api/governance/virtual-keys|teams|customers` and LiteLLM `/key/info`, `/team/info` return key->models->budget->team mappings, i.e., the AI-gateway route-to-identity map is directly readable — [Bifrost governance](https://docs.getbifrost.ai/features/governance), [LiteLLM virtual keys](https://docs.litellm.ai/docs/proxy/virtual_keys)
- Wiz's pitch for API SPM is exactly graph correlation: gateway config on the Security Graph alongside runtime resources and attack paths (vendor-claimed) — [Wiz author page](https://www.wiz.io/it-it/authors/gilad-hoze)

### Inferences
- **Route-to-identity map** = for every listener/route: which auth mechanism(s), which consumers/keys/JWT issuers/SPIFFE IDs can pass, which fall through anonymously, which upstream identity (mTLS cert, client cert, IAM role, service account) the gateway presents upstream. Inputs exist on every platform (Kong `/routes` + `/plugins` + `/consumers`; APIGW `GetRoutes`/`GetAuthorizers`; APIM policies; Istio `RequestAuthentication` + `AuthorizationPolicy` + `PeerAuthentication`; Linkerd `Server`+`AuthorizationPolicy`+`MeshTLSAuthentication`; LiteLLM/Bifrost key->model->team).
- **Effective-policy computation** must encode product-specific composition rules documented above (Istio ALLOW/DENY ordering and normalization; Kong multiple-auth-plugins OR semantics and `config.anonymous`; Envoy `failure_mode_allow`; Traefik middleware chain order; Gateway API ReferenceGrant/AllowedRoutes; Cilium `enableDefaultDeny`, `policyEnforcementMode`; Linkerd default-inbound-policy inheritance read only at pod creation). Nothing surveyed ships this as a product; it is the differentiator.
- **Mesh authorization graph** = node per workload identity (SA/SPIFFE), edge if some policy allows A->B on port/path; derived from Istio/Linkerd/Cilium CRDs plus Kubernetes NetworkPolicy (Istio says app can bypass sidecar so NetworkPolicy must be in the graph). Validate against runtime verdicts (Hubble `ALLOWED/DENIED/AUDITED`, Linkerd `authz_name` metrics) for "config says vs runtime does" drift.
- **Zero-trust score** inputs available from docs: % workloads with STRICT PeerAuthentication; % namespaces with default-deny; % Linkerd pods not on `all-unauthenticated`; % Cilium endpoints with enforcement enabled both directions; % gateway routes with non-anonymous auth; % upstreams with verified TLS (IST0128/0129 absent; APIM thumbprint validation on; APIGW.2/.10 pass); % keys with budgets/expiry (AI). Confidence-weight by evidence source (config vs runtime verdict).
- Buyers will also expect the audit/evidence trail items the Kong checklist and Linkerd/Cilium audit modes imply: who changed what (Konnect audit logs, APIM activity log, k8s audit for CRDs) and "audit-mode dry-run" of a proposed default-deny before enforcement.

### Gaps
- No source found describing any commercial product that computes cross-plugin effective policy for Kong/Traefik/Envoy or a cross-mesh authorization graph; absence in this research is not proof none exists (search budget ran out before checking Solo.io Gloo, Tetrate, Upwind, Sysdig, Aqua, ARMO/Kubescape, kube-bench style projects).
- `istioctl x authz check` / `istioctl proxy-config` as effective-policy evidence: known from prior knowledge, not re-verified.

### Inferences
- Tiering for the build: **Tier C (commodity, must-have for parity)** — the Security Hub / Defender / istioctl sets above, version-vs-CVE/EOL (Istio 1.28 EOL 2026-06-28; Kong 3.15 SAML fix; Traefik 3.7.7; ingress-nginx 1.12.1; LiteLLM 1.84.0 / 1.100.4+). **Tier B (differentiated but config-derivable)** — admin-plane reachability across all products, anonymous/fail-open fallbacks, regex-matcher lint, cross-namespace influence graph, secrets-in-config (Kong vaults, APIM Key Vault named values), declared-vs-live drift (decK/Konnect vs Admin API, Istio CRD vs `config_dump`, Traefik file vs `/api/rawdata`), AI-gateway key/budget/MCP hygiene. **Tier A (unique, graph-level)** — route-to-identity map, effective-policy per request, mesh authorization graph with runtime-verdict validation, confidence-weighted zero-trust score, toxic combos (anonymous route -> upstream with unverified TLS -> service that holds PII; AI key with no budget -> MCP server with shell tool).
