Method note: ~30 web searches/fetches were run (search budget was exhausted mid-task; several vendor doc URLs returned 404/redirects — Cilium Kafka L7 pages, Wiz academy/blog pages, Cyera integrations, Illumio Insights product page partially, Conduktor interceptor concepts). ## Key Question 1: Which runtime signals are obtainable agentlessly per system, which need a sensor/proxy, and what are the blind spots?

### Takeaway
Nearly every broker/gateway/cloud bus exposes an agentless authorization/authentication signal (Kafka authorizer log, Confluent/MSK authorizer logs, RabbitMQ event exchange, Redis ACL LOG, NATS /connz, Envoy/Istio access logs, Kong audit log, CloudTrail SQS/SNS data events, Azure RuntimeAuditLogs), but data-plane "who read/wrote what" is unevenly available: it is off-by-default-but-available on Confluent/Kafka (DEBUG authorizer or produce/consume audit categories), aggregated per-minute on Azure Premium only, absent on GCP Pub/Sub, and absent at payload level everywhere without a proxy. eBPF sensors cannot see inside TLS for JVM Kafka/AMQP clients without a JVM agent, so a Kafka-protocol proxy (Kroxylicious/Conduktor) or broker-side logs are the realistic enforcement/evidence points.

### Cited Findings

**Apache Kafka (self-managed) — agentless via broker logs**
- The open-source `kafka.authorizer.logger` logs access denials at INFO and allowed operations only at DEBUG; each entry includes principal, client host, operation, and resource. Conduktor gives log4j2 (`logger.authorizer.*`) vs log4j1 syntax and recommends `additivity=false` — [Confluent Developer course](https://developer.confluent.io/courses/security/audit-logs/); [Conduktor audit logging blog](https://conduktor.io/blog/kafka-audit-logging-compliance-forensics); [Netdata guide](https://www.netdata.cloud/guides/kafka/kafka-authorization-acl-denials/); [AxonOps docs](https://docs.axonops.com/data-platforms/kafka/security/authorization) (verified across four independent sources).
- Otterize's Kafka Watcher (beta) is an existence proof that a topic-level client→topic→operation access map can be built purely from authorizer logs: it requires `kafka.authorizer.logger=DEBUG` written to stdout, parses operation/topic/source host/allowed-or-denied, and yields topic-level (not record-level) visibility — [Otterize Kafka watcher docs](https://docs.otterize.com/reference/network-mapper/kafka-watcher) (verified).
- KIP-412 allows dynamically changing broker log levels via the Admin API (Kafka 2.4+), i.e. a product can raise authorizer logging to DEBUG without a broker restart — referenced in [Amazon MSK logging docs](https://docs.aws.amazon.com/msk/latest/developerguide/msk-logging.html) (verified).

**Confluent Platform — audit log**
- Requires `authorizer.class.name=io.confluent.kafka.security.authorizer.ConfluentServerAuthorizer`. Logs runtime authorization decisions (ACL and RBAC) as CloudEvents of type `io.confluent.kafka.server/authorization`, including check-only attempts that never execute. Default categories: Management and Authorize ON; produce, consume, interbroker OFF by default. Default topic `confluent-audit-log-events`, 90-day retention (7776000000 ms) only if the feature created the topic; routing configurable by subject/category/allow-deny with wildcards and to a separate cluster. Event `data` fields: serviceName, methodName (e.g. `kafka.CreateTopics`, `mds.Authorize`), resourceName, authenticationInfo (principal, principalResourceId, identity), authorizationInfo (granted, operation, resourceType, resourceName, patternType, rbacAuthorization/aclAuthorization, assignedPrincipals), request (correlation_id, client_id), requestMetadata (request_listener_name, request_id), clientAddress (ip, port, internal). Produce/consume logging "can grow very large"; docs recommend excluded principals — [Confluent Platform audit log concepts](https://docs.confluent.io/platform/current/security/compliance/audit-logs/audit-logs-concepts.html) (verified from primary doc).
- Confluent Cloud audit logs are "enabled by default"; Access Transparency events (`confluent.privileged.access`, event type `io.confluent.cloud/access-transparency`) log only successful Confluent-personnel access, require Premier support, Dedicated clusters, and explicit enablement — [Confluent Cloud access transparency overview](https://docs.confluent.io/cloud/current/monitoring/audit-logging/access-transparency-overview.html) (verified). The full Confluent Cloud category list/retention page was not successfully fetched (see Gaps).

**Amazon MSK — agentless**
- MSK Standard and Express brokers support both broker logs (INFO by default; dynamically settable to DEBUG/TRACE via KIP-412, with S3/Firehose recommended at DEBUG because CloudWatch "may continuously deliver a sample of logs") and a separate **authorizer logs** stream that "capture[s] authorization decisions made by your MSK cluster" to CloudWatch Logs, S3, or Firehose; configured via `logging-info`/`loggingInfo` on `create-cluster`/`update-monitoring` — [Amazon MSK logging](https://docs.aws.amazon.com/msk/latest/developerguide/msk-logging.html) (verified). MSK API calls are logged by CloudTrail (control plane); no MSK data-plane CloudTrail data events are described on this page.

**AWS SQS/SNS — CloudTrail data events (agentless, opt-in, billed)**
- SQS data events (resource type `AWS::SQS::Queue`) cover ChangeMessageVisibility(Batch), DeleteMessage(Batch), ReceiveMessage, SendMessage(Batch); must be enabled with advanced event selectors and can be filtered by `eventName`; announced Nov 2023 — [AWS CloudTrail data events](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html); [SQS announcement](https://aws.amazon.com//about-aws/whats-new/2023/11/amazon-sqs-support-logging-data-events-aws-cloudtrail); [SQS CloudTrail guide](https://docs.aws.eu/AWSSimpleQueueService/latest/SQSDeveloperGuide/logging-using-cloudtrail.html) (verified).
- SNS data events: `AWS::SNS::Topic` (Publish, PublishBatch) and `AWS::SNS::PlatformEndpoint` (Publish). Data events are not logged by default, not in Event History, and incur additional charges — [AWS CloudTrail data events](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html); [AWS blog on auditing SNS/SQS with data events](https://aws.amazon.com/blogs/mt/using-aws-cloudtrail-data-events-to-audit-your-amazon-sns-and-amazon-sqs-workloads/) (verified).

**Azure Service Bus / Event Hubs — diagnostic logs**
- `AZMSRunTimeAuditLogs` captures **aggregated** data-plane operations (send/receive) for Service Bus and Event Hubs, **Premium tier only**, with columns: ActivityName, AuthKey (Entra app ID or SAS policy name), AuthType (Entra ID or SAS), ClientIp, Count (ops per 1-minute aggregation window), NetworkType (Public/Private), Protocol, Provider (eventhub/relay/servicebus), Status (success or failure), Properties — [Azure Monitor AZMSRunTimeAuditLogs reference](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/azmsruntimeauditlogs) (verified). Other categories on the namespace: OperationalLogs (management), DiagnosticErrorLogs — [Supported logs for Microsoft.ServiceBus/Namespaces](https://learn.microsoft.com/en-sg/azure/azure-monitor/reference/supported-logs/microsoft-servicebus-namespaces-logs) (verified).

**GCP Pub/Sub — audit logs**
- "Pub/Sub does not currently write Data Access audit logs for message operations, such as Publish, Subscribe, and Acknowledge"; Publish, Pull, StreamingPull, Acknowledge produce no audit logs. ADMIN_WRITE methods (CreateTopic, DeleteTopic, UpdateSubscription, CreateSnapshot, CommitSchema) → Admin Activity logs; DATA_READ/ADMIN_READ methods (GetTopic, ListTopics, GetSubscription, GetIamPolicy, GetSchema, Seek) → Data Access logs. Service name filter `protoPayload.serviceName="pubsub.googleapis.com"`. Pub/Sub Lite (`pubsublite.googleapis.com`) does document DATA_READ/DATA_WRITE logs — [Pub/Sub audit logging](https://docs.cloud.google.com/pubsub/docs/audit-logging); [Pub/Sub Lite audit logging](https://docs.cloud.google.com/pubsub/lite/docs/audit-logging) (verified). A third-party article claiming a publish/subscribe log filter contradicts Google's docs — [SearchInform](https://searchinform.com/articles/cybersecurity/measures/log-management/gcp-audit-log/) (treat as unreliable).

**RabbitMQ — event exchange (agentless, in-band)**
- `rabbitmq_event_exchange` plugin republishes internal events to topic exchange `amq.rabbitmq.event` (default vhost `/`), including `connection.created`/`connection.closed`, `exchange.created`, `binding.deleted`, `user.created`, `user.authentication.success`/`user.authentication.failure` (bind `user.#`). Bodies are empty; properties are AMQP 0.9.1 headers or AMQP 1.0 annotations. Caveats: sensitive — restrict read access; churn can create large backlogs; recommend max-length of a few thousand on consuming queues — [RabbitMQ event exchange docs](https://www.rabbitmq.com/docs/event-exchange) (verified). Full routing-key catalog is in the "Internal events" logging section (not fetched).

**Redis — ACL LOG (agentless, pull)**
- `ACL LOG [count|RESET]` (since 6.0) lists failed AUTH/HELLO (reason=auth) and ACL violations by command, key, or pub/sub channel; each entry: count (events in a 60-second window), reason, context (toplevel/multi/lua/module), object, username, age-seconds, client-info (id, addr, laddr, name, user, cmd…), entry-id (sequence since process start, usable to detect lost entries), timestamp-created/last-updated. Returns up to 10 entries by default; the compatibility table marks it **not supported on Redis Software or Redis Cloud** — [Redis ACL LOG](https://redis.io/docs/latest/commands/acl-log/) (verified). It is an in-memory ring buffer, so a product must poll it and track entry-id to avoid loss (inference).

**NATS — monitoring endpoints (agentless, pull)**
- Monitoring HTTP port is off until `http_port`/`-m` is set, is plain HTTP, **unauthenticated by default** ("anyone who can reach the port can read data such as users and subjects"). `/connz` exposes per-client cid, account, `authorized_user` (with `auth=true`), rtt, pending_bytes, `subscriptions_list` (with `subs=true`), with query params acc/subs/auth/sort/limit/offset; `/varz` gives connections, total_connections, in/out msgs, slow_consumers; `/routez`, `/jsz` (streams, consumers, per-account details; unscoped `/jsz` on large nodes can time out); `/healthz`. The fetched page did not document `/accountz`, `/subsz`, `/leafz` — [NATS monitoring docs](https://docs.nats.io/running-a-nats-service/nats_admin/monitoring) (verified for what is listed).

**API gateways / service mesh**
- Kong Gateway audit logs: Admin API requests via `/audit/requests` (with RBAC user id/name, workspace UUID, Kong Manager login/logout) and DB changes via `/audit/objects` (entity, primary key, create/update/delete, linked by `request_id`); off by default (`audit_log`), TTL via `audit_log_record_ttl`, optional RSA signing for non-repudiation; depends on Enterprise-tier features (RBAC, Workspaces, Kong Manager) — [Kong audit logs](https://developer.konghq.com/gateway/audit-logs/) (verified). Proxy access-log fields were not covered on that page.
- Istio: Envoy access logs are enabled mesh-wide/namespace/workload via the `Telemetry` API (`accessLogging.providers: envoy`) or `meshConfig.accessLogFile`; the default format includes START_TIME, method/path, RESPONSE_CODE, RESPONSE_FLAGS, RESPONSE_CODE_DETAILS, UPSTREAM_HOST, UPSTREAM_CLUSTER_RAW (e.g. `inbound|8000||`), DOWNSTREAM_REMOTE_ADDRESS, REQUESTED_SERVER_NAME, ROUTE_NAME — but **no peer-certificate/SPIFFE identity field by default** — [Istio access log task](https://istio.io/latest/docs/tasks/observability/logs/access-log/) (verified). Envoy's `%DOWNSTREAM_PEER_URI_SAN%` etc. exist as custom operators but the definitions page was not successfully extracted (Gap).

**eBPF sensors and the TLS blind spot**
- Standard eBPF TLS capture hooks OpenSSL-style library functions; the JDK encrypts in Java code with no exported `SSL_write`-like symbols, so uprobes have nothing to attach to. Coroot's workaround attaches a JVM agent (~15% CPU in its benchmark vs ~38% for the OTel Java agent; HotSpot only) — [Coroot: Java TLS instrumentation with eBPF](https://coroot.com/blog/java-tls-instrumentation-with-ebpf/) (vendor benchmark).
- Observability Summit NA 2026 (OBI/Grafana Beyla lineage) slides: HTTPS, gRPC and "encrypted DB/Kafka traffic" are cases where the kernel sees only ciphertext; approach is injecting a small agent into the JVM and capturing decrypted traffic via `sys_ioctl` instrumentation; difficulties include JDK diversity, JIT symbol addresses, virtual-thread correlation, and no uprobe support for anonymous JIT code regions — [OBI Java eBPF talk slides](https://hosted-files.sched.co/observabilitysummitna26/a7/2026-05-22-obs-summit-ebpf-java.pdf).
- Fallback recommended by SkyWalking for Java services is to analyze traffic in an Envoy/Istio sidecar — [SkyWalking SWIP-2](https://skywalking.incubator.apache.org/docs/main/next/en/swip/swip-2).
- Tetragon (Isovalent) parses DNS, TLS handshake metadata, HTTP, UDP, TCP tied to process ancestry; Kafka is not named in any fetched result — [Isovalent Tetragon](https://isovalent.com/tetragon); [Isovalent host-based visibility brief](https://isovalent.com/briefs/host-based-kubernetes-visibility/) (vendor). Falco event sources are `syscall` (kernel driver/eBPF, or `nodriver`) plus plugins (CloudTrail, k8saudit family, Okta); no application-protocol (Kafka/AMQP) or TLS payload decoding is documented — [Falco event sources](https://falco.org/docs/concepts/event-sources/) (verified). Sysdig/Falco are syscall-level ("tcpdump for system calls") — [Wireshark blog](https://www.wireshark.org/blog/2023-09-27-the-evolution-of-system-introspection-from-bpf-to-wireshark-to-falco).

**OpenTelemetry as a source**
- Kafka client instrumentation via `TracingProducerInterceptor`/consumer interceptor creates send/receive spans; semantic conventions define Send (PRODUCER), Poll (CONSUMER), Process (SERVER), Commit (CLIENT) spans with `messaging.system=kafka`, destination/topic, consumer group, partition, offset; context propagates in W3C `traceparent` record headers; attribute names changed across versions (`messaging.operation` split into `messaging.operation.name`/`.type` in conventions v1.43.0) — [OpenTelemetry blog: Instrumenting Kafka clients](https://opentelemetry.io/blog/2022/instrument-kafka-clients/); [Kafka semantic conventions 1.27](https://opentelemetry-semantic-conventions.hexdocs.pm/1.27.0/kafka.html); [.NET ConfluentKafka instrumentation changelog](https://newreleases.io/project/github/open-telemetry/opentelemetry-dotnet-contrib/release/Instrumentation.ConfluentKafka-0.2.0-alpha.1) (verified).

**Proxies as enforcement points**
- Kroxylicious: open-source Kafka protocol proxy (Red Hat/IBM-backed, Commonhaus Foundation); filters implement `RequestFilter`/`ResponseFilter` or API-specific interfaces (`MetadataRequestFilter`, `FetchResponseFilter`), loaded via `ServiceLoader`; `RecordEncryption` with pluggable KMS; an experimental `Authorisation` filter with `AclAuthoriser` rules file that "logs production warnings"; a `ResponseOrderer` keeps FIFO responses per connection. No audit/logging filter is documented in the README — [Kroxylicious README](https://raw.githubusercontent.com/kroxylicious/kroxylicious/main/README.md) (verified); overview claims governance/security/policy/audit "without changing applications or the Kafka cluster" — [Kroxylicious overview](https://scour.ing/p/https://kroxylicious.io/overview) (vendor). Conduktor's comparison page (vendor marketing) says Kroxylicious ships record encryption and schema validation and the rest is "a filter you write" — [Conduktor vs Kroxylicious](https://www.conduktor.io/compare/conduktor-gateway-vs-kroxylicious.md).
- Conduktor Gateway: Kafka-compliant proxy between clients and Confluent/MSK/Redpanda/Aiven/Apache Kafka; central field-level or full-payload encryption, masking at the proxy, policies (rate limits, data-quality rules, topic-creation constraints), PLAINTEXT/SSL/SASL_SSL/mTLS, "interceptors" as plugin mechanism — [Conduktor Gateway docs](https://docs.conduktor.io/gateway/) (vendor docs); vendor marketing claims "complete audit logs of all data access and administrative actions", licensed per cluster on Enterprise, Community edition limited to cross-network reachability — [Conduktor kafka security](https://conduktor.io/product/kafka-security); [Conduktor comparison](https://www.conduktor.io/compare/conduktor-gateway-vs-kroxylicious.md) (vendor-claimed).
- Kai Waehner's analysis: proxies (Kroxylicious, Conduktor, Confluent) enable encryption, access control, compliance without modifying clients or brokers — [Kafka Proxy Demystified](https://www.kai-waehner.de/blog/2025/10/30/kafka-proxy-demystified-use-cases-benefits-and-trade-offs/).
- OPA Kafka plugin exists as an external authorizer (decision logs are a potential evidence source) — [StyraInc/opa-kafka-plugin](https://github.com/StyraInc/opa-kafka-plugin).

### Inferences
- Agentless matrix (from the above): Kafka OSS = authorizer log (denials free, allows need DEBUG, no payload); Confluent Platform/Cloud = structured CloudEvents incl. principal, client IP, client_id, listener, granted flag (produce/consume opt-in, high volume); MSK = native authorizer log stream to CloudWatch/S3/Firehose (strong, cheap to adopt); SQS/SNS = per-message API events via CloudTrail (opt-in, billed; includes IAM principal); Azure SB/EH = per-minute aggregated counts with AuthKey/ClientIp/NetworkType/Status (Premium only, no per-message detail); GCP Pub/Sub = **no data-plane evidence at all** (control-plane only) — a product must fall back to metrics, subscription state, or client-side OTel; RabbitMQ = authn and connection lifecycle via event exchange (consumed in-band, needs a queue + credentials); Redis = ACL LOG polling (denials/auth failures only, volatile, absent on Redis Cloud/Software); NATS = connection/subscription snapshot polling (no history, port often unauthenticated — itself a finding); Kong = admin/config audit (Enterprise); Istio = per-request access logs, identity only if the format is customised.
- Sensor need: payload-level (DSPM-grade) or per-record evidence on TLS Kafka/AMQP from JVM clients requires either (a) a Kafka-protocol proxy (Kroxylicious/Conduktor) that terminates TLS, (b) client-side interceptors/OTel, or (c) a JVM agent; eBPF alone is insufficient for Java (the dominant Kafka client ecosystem) and no fetched eBPF vendor documents a Kafka/AMQP parser. Cilium's L7 Kafka policy (beta) exists but its docs could not be fetched this run; it would in any case see cleartext only (unverified here).
- Blind spots a product must disclose: allowed-operation evidence absent at default Kafka log levels; Azure aggregation hides individual messages; Pub/Sub message ops invisible; Redis ACL LOG overwrites; NATS gives no retrospective data; Istio default logs lack SPIFFE identity.

## Key Question 2: What node/edge model and toxic-combination rules do graph leaders use, and what does "proven reachable" require?

### Takeaway
Leaders (Wiz, Orca, XM Cyber, Illumio) converge on a graph where risk = path from an exposure (internet-facing endpoint/API, exploitable vuln) through identity/permission edges to a sensitive asset, scored by exploitability × exposure × data sensitivity; "proven" reachability is increasingly claimed via active probing (Wiz Red Agent) or observed flow data (Illumio) rather than static config alone, and choke-point analysis prioritises the ~2% of exposures where paths converge. Primary vendor docs on exact node/edge schemas were not retrievable; findings are mostly vendor marketing.

### Cited Findings
- Wiz API SPM: toxic combination = "situations where an exposed API forms part of an attack path that could lead to compromise of sensitive data or abuse of resources"; the Security Graph joins API and cloud context with exposure, vulnerabilities and sensitive-data access; example critical path = internet-facing API endpoint + confirmed SQL injection + VM holding PII; Wiz adds a dynamic testing layer ("Red Agent") that probes endpoints "the way an attacker would" to confirm issues passive scanning may miss — [Wiz blog: Introducing Wiz API SPM](https://www.wiz.io/blog/introducing-wiz-api-spm) (vendor-claimed).
- Third-party explainer: individually low-severity issues combine into a critical path, e.g. exposed VM that can reach a database holding customer data — [Security Boulevard](https://securityboulevard.com/2025/04/wizs-security-graphdb-vs-deeptempos-loglm); [SecurityScientist Q&A](https://answers.securityscientist.net/q/2044/how-does-wiz-identify-toxic-combinations) (secondary).
- Orca: attack path analysis chains weaknesses enabling lateral movement toward critical assets; features include timelines, risk **blast radius** (how many assets a risk affects, which are crown jewels, access paths exposing it), **choke point detection**, and an "Orca Score" per path from exploitability, internet exposure, data sensitivity, regulatory impact — [Orca blog: multi-cloud attack path analysis](https://orca.security/resources/blog/multi-cloud-attack-path-analysis-for-strategic-remediation/); [SecurityScientist](https://answers.securityscientist.net/q/26147/how-does-attack-path-analysis-work) (vendor-claimed).
- XM Cyber / Cyentia: choke points are "entities through which multiple attack paths converge en route to critical assets"; about 2% (~200) of a typical organisation's ~11,000 exposures sit on choke points; ~1 in 4 choke points exposes ≥10% of critical assets; prioritising critical choke points reduces remediation scope by 99.6% — [Cyentia: Value of Choke Points](https://www.cyentia.com/value-of-choke-points/) (research on XM Cyber data, 2023).
- Illumio Insights: "AI security graph", agentless, maps "every east-west traffic flow across your hybrid environment", scores lateral-movement risk from actual network flows rather than static rules, flags policy gaps and excessive access, tracks unusual outbound (exfiltration), and offers one-click containment / quarantine of compromised workloads and connection lockdown — [Illumio Insights](https://www.illumio.com/products/illumio-insights) (vendor-claimed; "blast radius" not on the page).
- Vorlon (SaaS/NHI): DataMatrix (April 2025) focuses on SaaS API traffic and identities; customer quote describes clicking into a SaaS app to "see all the other apps, services, and secrets connecting to it"; Vorlon research: >50% of SaaS apps fail basic logging requirements and 40% cannot distinguish human from machine activity — [GlobeNewswire release](https://www.globenewswire.com/news-release/2025/04/16/3062609/0/en/Vorlon-s-DataMatrix-Cracks-Open-Black-Box-of-SaaS-Ecosystem-Security-to-Eliminate-Blind-Spots.html) (vendor-claimed). Comparable NHI graphs: Obsidian traces employee → OAuth app → token → service account → data source — [Sacra](https://sacra.com/chat/h/a6817f71-4d7e-4db7-846e-15213492d650/) (secondary). SpecterOps OpenGraph generalises BloodHound-style attack graphs beyond AD — [SpecterOps OpenGraph](https://specterops.io/opengraph/).
- Access-path evidence for Kafka specifically can be derived from authorizer logs (Otterize approach) giving client→topic→operation edges — [Otterize Kafka watcher](https://docs.otterize.com/reference/network-mapper/kafka-watcher) (verified).

### Inferences
- A minimal node set for an integration-layer graph, consistent with the vendors above: Principal (user, service account, API key, NHI/OAuth app), Credential/Secret, Network endpoint (listener, LB, gateway route, VPC/subnet/SG), Broker/Cluster, Topic/Queue/Subject/Channel, Schema/Field tag, Consumer group, Workload (pod/VM/function), Data class (PII etc.), Vulnerability/misconfig. Edge set: CAN_AUTH (credential→principal), CAN_READ/WRITE/ADMIN (principal→resource, from ACL/RBAC/IAM), OBSERVED_READ/WRITE (from audit logs — the "runtime-proven" edge), REACHES (network path), EXPOSED_TO_INTERNET, CONTAINS (topic→data class), RUNS_AS (workload→principal).
- Toxic-combination rules that map directly from leader patterns: (internet-exposed listener ∧ no/weak authn) ; (internet-exposed ∧ topic contains PII) ; (over-privileged principal (wildcard ACL / cluster admin) ∧ credential in plaintext/secret store misconfig) ; (reachable broker ∧ unauthenticated monitoring/admin port e.g. NATS /connz) ; (principal with READ on PII topic ∧ no observed use in N days = stale privilege). "Proven" should mean: static policy says allowed AND (runtime log shows allowed op OR active probe succeeds); mark everything else "potential".
- Internet-reachability proof in the broker world = three independent signals: cloud config (public IP/LB + SG/NSG rule), external observation (Censys/Shodan/own scanner sees the port and protocol banner/ApiVersions response), and, if authorised, an unauthenticated protocol handshake (e.g. Kafka ApiVersions, AMQP connection.start) — see Q4.

- Wiz's actual graph entity/relationship schema and "effective exposure" algorithm: academy/blog pages 404'd; only marketing claims available.
- Prisma Cloud and CrowdStrike attack-path details: no sources retrieved (search budget exhausted).
- Independent evaluation of any vendor's reachability-validation accuracy: none found.

## Key Question 3: What does DSPM on streaming data look like in practice and who does it?

### Takeaway
Only BigID documents a native Kafka/Confluent scanning connector (agentless, sampling-based, schema-registry-aware); Sentra's integrations page lists no streaming source, Cyera's could not be fetched, and Macie is S3-only (not verified this run). The practical "DSPM at the bus" pattern is schema-based: Confluent Stream Catalog tags (`confluent:tags`, e.g. PII) drive CSFLE encryption and masking rules, so a security product can classify by schema metadata without touching payloads, and use consented sampling only where schemas are absent.

### Cited Findings
- BigID: "connects securely to Kafka using agentless integration to scan streaming data across topics and partitions"; supports Apache Kafka core, Confluent Kafka, Avro with schema-registry integration; "scans a sample quantity of messages on every poll interval"; configurable sampling/polling "to align discovery with throughput and latency requirements"; findings include personal identifiers, credentials, application logs, regulated records; can link to downstream storage/SaaS/AI — [BigID Kafka coverage](https://bigid.com/data-coverage/kafka/); [BigID for Confluent and Kafka](https://bigid.com/partner/confluent-kafka/) (vendor-claimed). JSON/Protobuf support, consumer-group behaviour and Confluent Cloud specifics are not documented on the page.
- Sentra: integrations page lists 27 outbound integrations (Slack, Jira, Splunk, Sentinel, Wiz, Torq, etc.); Kafka, Confluent, Kinesis, Pub/Sub are not listed; Sentra positions itself as agentless, API-based, scanning in place — [Sentra integrations](https://www.sentra.io/integrations); [Sentra vs BigID](https://www.sentra.io/sentra-vs-bigid) (vendor; absence of listing ≠ absence of support).
- Confluent CSFLE: envelope encryption with KEK in external KMS (AWS KMS, Azure Key Vault, GCP KMS) and DEKs managed by the Schema Registry DEK Registry (scoped by subject); fields are selected by schema tags (Avro example tags SSN field `PII`/`PRIVATE`; Cloud uses `confluent:tags`), tag definitions must exist in Stream Catalog before registering the schema; encryption rules map tag → key with RBAC for encrypt/decrypt; requires Stream Governance Advanced on Cloud; supported clients Java (CP 7.4.5+), Go 2.5.0+, .NET 2.5.0+; masking rules can operate by field name — [Confluent Cloud CSFLE docs](https://docs.confluent.io/cloud/current/security/encrypt/csfle/client-side.html); [Confluent Platform CSFLE](https://docs.confluent.io/platform/current/security/protect-data/csfle/client-side.md); [Flink + CSFLE guide](https://docs.confluent.io/cloud/current/flink/how-to-guides/client-side-field-level-encryption.html); [Confluent blog: protect PII with data contracts](https://www.confluent.io/fr-fr/blog/protect-pii-kafka-data-contracts/) (verified from primary docs).
- Practitioner patterns: classification catalogue distinguishing direct vs quasi-identifiers with per-field handling rules; detection combines regex and ML applied at ingestion via stream processors or Kafka Connect SMTs; carrying classification in Kafka record headers (e.g. a `pii-fields` header) so governance tools read metadata without the payload — [Conduktor PII detection glossary](https://conduktor.io/glossary/pii-detection-and-handling-in-event-streams); [Conduktor classification/tagging](https://conduktor.io/glossary/data-classification-and-tagging-strategies); [Lenses: life of PII in Kafka](https://lenses.io/blog/life-of-pii-data-masking-and-compliance-for-apache-kafka/) (vendor content).
- Proxy-layer masking/encryption (Conduktor Gateway field-level encryption and masking; Kroxylicious RecordEncryption) enables enforcement without client changes — [Conduktor Gateway docs](https://docs.conduktor.io/gateway/); [Kroxylicious README](https://raw.githubusercontent.com/kroxylicious/kroxylicious/main/README.md) (verified).

### Inferences
- A read-only product can deliver "schema-based DSPM" with zero payload access: pull Schema Registry subjects/versions, Stream Catalog tags, CSFLE encryption rules and masking rules; derive which topics carry tagged PII, whether those fields are protected by a CSFLE rule, and which principals hold READ ACLs on them (toxic combo: PII-tagged field ∧ no encryption rule ∧ wildcard READ ACL).
- Payload sampling (BigID-style) is a differentiator but requires explicit consent, a dedicated consumer principal with least-privilege READ, bounded sampling (N records/partition, time-boxed), and audit of the sampling itself — the Confluent audit-log excluded-principal mechanism shows how to keep the scanner's own reads out of audit noise.
- PII in logs (broker/authorizer logs contain principal names, client IPs, topic names but not payloads) is lower-risk than PII in topics; but produce/consume audit categories and DEBUG client logs can leak record keys — a product should classify its own ingested logs.

## Key Question 4: What EASM/discovery features matter and how do vendors avoid scanning what they don't own? What does "internet-reachable" proof look like?

### Takeaway
runZero scopes external scans by user-supplied ASNs/domains/IPs plus Shodan/Censys-derived hosts (including TLS-cert common-name matches), shows a resolved-scope sample for confirmation before scanning, and reports banners/fingerprints and exposure findings (e.g. "databases on public IPs"); it documents no cryptographic ownership verification. Censys/Shodan scan the whole internet and offer opt-out/blocking rather than verification. No measurement study of exposed Kafka brokers on 9092 was found.

### Cited Findings
- runZero external scanning: inputs `asn4:<n>`, `domain:<name>` (pulls subdomains), `public:all` (public IPs found in internal scans), plus Shodan/Censys imports that can add hosts outside your ASNs/domains "such as hosts whose TLS certificate common name contains your domain"; shows a sample of the resolved scope for confirmation; scans from a runZero-hosted zone; adjustable rate; recommends DigitalOcean for self-hosted explorers because other clouds rate-limit outbound scanning; outputs include open ports/banners/versions, inferred software, Chrome screenshots, findings for EOL OS, SSH password auth, shared SSH host keys, **databases on public IPs**, leaked RFC1918 addresses, unusual high-port services; External Assets Report and new-asset alert rules — [runZero external scanning blog](https://www.runzero.com/blog/external-scanning) (verified). runZero combines active scanning, passive discovery, and API integrations and can run "without agents, authentication, or appliances" — [runZero docs](https://help.runzero.com/docs/what-is-runzero/).
- Censys: publishes scanner subnets, ASNs (AS398722, AS398705, AS398324) and user agent `CensysInspect/1.1`; operators opt out by firewall-blocking; blocking stops future indexing but not historical data; hosts drop from Search 24–48h after last observation; states it never attempts to log in; abuse contact censys-abuse@censys.com; no requester-ownership verification described — [Censys opt-out](https://docs.censys.com/docs/opt-out-of-data-collection) (verified).
- Shodan/Censys model per runZero: "scan the whole world" and network owners "can ask to exclude their IP ranges for all users" — [runZero external scanning blog](https://www.runzero.com/blog/external-scanning).
- Kafka exposure detection in the wild targets the web UI (`http.title:"UI for Apache Kafka"`), not the broker protocol — [Vidoc module](https://app.vidocsecurity.com/public-library/apache-kafka-unauthorized-ui-exposure-5pw99). Precedent methodology: Trend Micro used Shodan to find 243,469 exposed Kubernetes kubelet ports, most returning 401 — [Trend Micro](https://trendmicro.com/en_ca/research/22/e/the-fault-in-our-kubelets-analyzing-the-security-of-publicly-exposed-kubernetes-clusters.html).
- NATS monitoring port is unauthenticated by default and leaks users/subjects if reachable — [NATS monitoring](https://docs.nats.io/running-a-nats-service/nats_admin/monitoring) (verified) — a concrete fingerprintable exposure.

### Inferences
- Ownership-safe discovery for a read-only product: (1) seed from cloud inventory joins (MSK/Service Bus/Pub-Sub/Kafka-on-EC2 resources with public endpoints, from the customer's own cloud credentials — unambiguously owned); (2) seed from customer-declared ASNs/domains with the runZero-style scope preview; (3) corroborate with Censys/Shodan passive data (no packets sent by the product); (4) only active-probe hosts that appear in (1) or are DNS/cert-attributable to declared domains; (5) log every probe with the authorising user for the customer's own audit.
- "Internet-reachable" proof hierarchy (strongest first): (a) product's own unauthenticated protocol handshake from an external vantage (Kafka ApiVersions / SASL mechanism list; AMQP connection.start; Redis `PING`/`HELLO` error; NATS INFO banner, `/varz`) — most convincing but must be consent-gated; (b) third-party observation (Censys/Shodan record with port + service fingerprint + timestamp); (c) cloud-config inference (public IP/LB + 0.0.0.0/0 ingress on 9092/5672/6379/4222/8222) — necessary but weaker (NACLs, host firewalls, mesh policy may block). Vendors like Wiz claim (a)-style validation via "Red Agent" for APIs — [Wiz API SPM](https://www.wiz.io/blog/introducing-wiz-api-spm).
- Internal broker fingerprinting features that matter: protocol-level identification (ApiVersions response, AMQP server-properties, Redis INFO, NATS INFO) over banner guessing; TLS/SASL mechanism enumeration; version → CVE mapping; default-credential checks only with explicit opt-in.

## Key Question 6: Detection and response for the integration layer (behavioural baselines per principal, anomaly detection, SOAR hooks, revoke/rotate, Kafka ACL quarantine); what buyers expect and what is safe for a read-only product

### Takeaway
Security-specific behavioural baselining for brokers is thinly documented; the closest public material is Uber's operational consumer-group anomaly detection and Confluent's ksqlDB SIEM demos. Response actions buyers see elsewhere (Illumio one-click containment/quarantine, Orca/Wiz remediation) imply expectations, but for a read-only product the safe pattern is evidence → recommended reversible change (ACL deny-add, credential rotation ticket) → approval → execution by the customer's own tooling (SOAR/GitOps), with every proposed change expressed as a diff that can be reverted.

### Cited Findings
- Uber uGroup: alerts on abnormal consumer behaviour — high offset-commit frequency, many randomly created consumer groups, high lag across many groups, constant rebalancing — [Uber Engineering: uGroup](https://eng.uber.com/introducing-ugroup-ubers-consumer-management-framework/) (operational, not security-focused).
- Confluent "Seamless SIEM" series: learn normal behaviour from osquery logs over Kafka, score events with an LDA model in ksqlDB, route into good/bad/ugly topics — [Confluent blog](https://www.confluent.io/fr-fr/blog/siem-with-anomaly-detection-using-machine-learning-and-ksqldb/) (demo-level).
- Anomaly taxonomies for streams (availability, throughput, ordering, duplication/loss; timestamp drift causes false alerts) — [Gravitee corpus](https://www.gravitee.io/corpus/gen-1930/endpoint-detection-and-response/kafka-event-stream-anomalies.html) (vendor, low quality).
- Confluent audit logs capture **denied** and check-only authorization attempts with principal, client IP and client_id — the raw material for per-principal baselines — [Confluent audit log concepts](https://docs.confluent.io/platform/current/security/compliance/audit-logs/audit-logs-concepts.html) (verified). Redis ACL LOG and RabbitMQ `user.authentication.failure` give the equivalent auth-failure signal — [Redis ACL LOG](https://redis.io/docs/latest/commands/acl-log/); [RabbitMQ event exchange](https://www.rabbitmq.com/docs/event-exchange) (verified).
- Illumio Insights: "one-click containment", quarantine compromised workloads, connection lockdown, AI-guided remediation plan with policy recommendations — [Illumio Insights](https://www.illumio.com/products/illumio-insights) (vendor-claimed).
- Falco Talon exists as a response engine for Falco events — [Falco Talon v0.3.0 blog](https://v0-43.falco.org/blog/falco-talon-v0-3-0/) (noted, not detailed).
- Vorlon research: 40% of SaaS apps cannot distinguish human from machine activity — a limitation for NHI baselining — [GlobeNewswire](https://www.globenewswire.com/news-release/2025/04/16/3062609/0/en/Vorlon-s-DataMatrix-Cracks-Open-Black-Box-of-SaaS-Ecosystem-Security-to-Eliminate-Blind-Spots.html) (vendor research).
- Enforcement points that can quarantine in-line without touching brokers: Kroxylicious experimental Authorisation filter with ACL rules file; Conduktor Gateway policies — [Kroxylicious README](https://raw.githubusercontent.com/kroxylicious/kroxylicious/main/README.md); [Conduktor Gateway docs](https://docs.conduktor.io/gateway/) (verified/vendor).

### Inferences
- Per-principal baseline features (derivable from Q1 sources): set of topics/queues touched, operations, client IPs/listeners, client_id strings, hourly volume (Azure Count, CloudTrail event counts, Confluent produce/consume if enabled), consumer-group membership; anomalies = first-seen topic for principal, first-seen source network (NetworkType flip Private→Public on Azure), burst of denials (Confluent denied events, Redis ACL LOG count, RabbitMQ auth failures), new consumer group on PII topic, offset reset to earliest on a sensitive topic (consumption replay), credential used from two geographies.
- Safe response catalogue for a read-only product (approval-gated, reversible): (1) open ticket/SOAR webhook with evidence bundle; (2) propose exact ACL/IAM diff (e.g. add explicit DENY for principal on topic — Kafka DENY ACLs override ALLOW, so it is additive and reversible by deleting the DENY) rather than deleting existing ALLOWs; (3) propose API-key/SAS-policy rotation with a rollback window; (4) propose quota throttling (Kafka client quotas) as a soft quarantine; (5) propose Gateway/proxy policy if customer runs Kroxylicious/Conduktor; execution via customer's own credentials/pipeline, never the product's read-only ones. Destructive actions (delete topic, revoke all ACLs, delete user) should never be auto-executed.

## Cross-cutting: Table-stakes vs differentiator vs emerging (2026)

### Takeaway
Table-stakes = agentless inventory + management audit ingestion + exposure findings + ACL/IAM over-privilege; differentiators = runtime-proven access edges from authorizer/data-event logs, schema-tag-driven DSPM with CSFLE gap detection, consent-gated external reachability proof, and choke-point prioritisation on an integration-specific graph; emerging = proxy-based enforcement (Kroxylicious/Conduktor), eBPF-with-JVM-agent decryption, and NHI/SaaS graphing (Vorlon/Obsidian style).

### Cited Findings
- Agentless cloud/API-based discovery and graph-based toxic-combination analysis are the stated baseline of CNAPP/DSPM leaders — [Wiz API SPM](https://www.wiz.io/blog/introducing-wiz-api-spm); [Orca](https://orca.security/resources/blog/multi-cloud-attack-path-analysis-for-strategic-remediation/); [Sentra](https://www.sentra.io/sentra-vs-bigid) (vendor).
- Choke-point prioritisation is validated by independent analysis (2% of exposures, 99.6% scope reduction) — [Cyentia](https://www.cyentia.com/value-of-choke-points/).
- Broker-native audit streams now exist on MSK (authorizer logs), Confluent (CloudEvents audit), Azure Premium (RuntimeAuditLogs), AWS SQS/SNS (CloudTrail data events) — see Q1 sources (verified) — making "runtime-proven" edges feasible without sensors.
- eBPF TLS visibility for Java still requires JVM agent injection as of the May 2026 Observability Summit — [OBI slides](https://hosted-files.sched.co/observabilitysummitna26/a7/2026-05-22-obs-summit-ebpf-java.pdf).
- Proxy-based governance is positioned by analysts as the emerging pattern for Kafka — [Kai Waehner, Oct 2025](https://www.kai-waehner.de/blog/2025/10/30/kafka-proxy-demystified-use-cases-benefits-and-trade-offs/).

### Inferences
- Feature inventory for a best-in-class integration-layer product (grouped):
  - Table-stakes: cloud/API inventory of brokers, gateways, meshes; ACL/RBAC/IAM effective-permission analysis; public-exposure findings from config; ingestion of management audit events; config snapshot/diff; SIEM/ticketing export.
  - Differentiators: OBSERVED edges from authorizer/data-event logs (with explicit "evidence level" per edge); Pub/Sub-style "no data-plane evidence" honesty flags; schema-tag DSPM + CSFLE/masking coverage gaps; consent-gated external handshake proof; integration-specific toxic combos and choke points; stale-privilege (allowed but never observed) findings; approval-gated reversible remediation diffs.
  - Emerging/optional: optional proxy or client-interceptor module for payload-level evidence and enforcement; JVM-agent-assisted eBPF; NHI/SaaS connector graph.
