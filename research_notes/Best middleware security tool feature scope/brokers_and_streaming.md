## KQ1. Full checklist of posture controls per system (auth, authz/ACL, TLS, listener exposure, default accounts, quotas, durability, logging/audit, encryption at rest, plugin/extension risk, management UI exposure, version/EOL/CVE), plus the authoritative guide, the 2023-2026 incidents, the read-only evidence APIs, and what competitors already check

### Takeaway
No CIS benchmark exists for Kafka, RabbitMQ, or Redis (only Cassandra, MongoDB, and the Azure managed-service baseline incl. Azure Cache for Redis), so the "authoritative guide" for every self-managed broker is the vendor's own security documentation plus the vendor CVE list; the recurring, incident-proven failure pattern across every system is the same: an unauthenticated default (Kafka PLAINTEXT://:9092 with no authorizer, Redis `default on nopass ~* +@all`, NATS "admits every connection", HiveMQ allow-all extension, kafka-ui/Kafdrop no auth, RabbitMQ `guest/guest`, ActiveMQ Jolokia/REST unsecured by default) combined with a management/metadata endpoint reachable from the wrong network. Cloud CSPM (Prowler, Datadog) covers only the cloud-managed surfaces (MSK/SQS/SNS/Kinesis/EventBridge/ElastiCache) and almost nothing inside the broker (ACLs, consumer groups, connectors, schema registry, listeners), which is the open space.

Authoritative guide: the Security chapter of the Apache Kafka documentation and the broker config reference; the Apache CVE list.
- Broker config defaults (Kafka 4.1 config reference): `listeners` default `PLAINTEXT://:9092`; `auto.create.topics.enable` default `true`; `delete.topic.enable` default `true`; `unclean.leader.election.enable` default `false`; `min.insync.replicas` default `1`; `default.replication.factor` default `1`; `offsets.topic.replication.factor` default `3`; `transaction.state.log.replication.factor` default `3`; `log.retention.hours` default `168`; `controller.listener.names` default `null`; `sasl.enabled.mechanisms` default `GSSAPI`; `connections.max.reauth.ms` default `0` (no session-lifetime limit); `remote.log.storage.system.enable` default `false` — [Kafka 4.1 broker configs](https://kafka.apache.org/41/generated/kafka_config.html)
- The same reference page was truncated before `authorizer.class.name`, `allow.everyone.if.no.acl.found`, `super.users`, `listener.security.protocol.map`, `security.inter.broker.protocol`, `ssl.client.auth`, `ssl.endpoint.identification.algorithm`, `ssl.enabled.protocols`; these keys are the standard posture surface but their defaults were not captured in this session (see Gaps) — [Kafka 4.1 broker configs](https://kafka.apache.org/41/generated/kafka_config.html)

  - CVE-2026-33557 (4.1.0-4.1.1 -> 4.1.2/4.2.0): default OAUTHBEARER validator accepts JWTs without checking signature, issuer, or audience.
  - CVE-2026-35554 (clients 2.8.0-4.1.1 -> 3.9.2/4.0.2/4.1.2/4.2.0): producer buffer-pool race can silently deliver messages to the wrong topic.
  - CVE-2025-27819 (2.0.0-3.3.2 -> 3.9.1/4.0.0): JndiLoginModule in SASL JAAS config via AlterConfigs on brokers -> RCE/DoS.

#### RabbitMQ (incl. CloudAMQP)
Authoritative guide: RabbitMQ access-control docs.
- Default user `guest`/`guest` has full access to vhost `/` on a blank node; `loopback_users` restricts `guest` to localhost by default; `loopback_users = none` allows remote guest login and is strongly advised against; refused logins log "PLAIN login refused: user 'guest' can only connect via localhost" — [RabbitMQ access control](https://www.rabbitmq.com/docs/access-control)
- Permissions are per-vhost regex triples (configure/write/read); `'^$'` blocks everything; from 4.3.1 passive declarations need at least one permission; topic permissions apply to topic exchanges and are allowed by default when none are defined; `auth_backends.N` aliases `internal` (default), `ldap`, `oauth`/`oauth2`, `http`, `dummy`; first positive result in a chain is final; authn/authz splittable (`auth_backends.1.authn = ldap`, `auth_backends.1.authz = internal`); tags only gate management UI (`default_users.monitoring.tags = monitoring`); listing via `rabbitmqctl list_users`, `rabbitmqctl list_permissions`, `rabbitmqadmin users list`, `rabbitmqadmin users permissions`; `PUT /api/users/{user}` in HTTP API — [RabbitMQ access control](https://www.rabbitmq.com/docs/access-control)
- CVE-2026-57219 (published 2026-07-10; CWE-200; CVSS v4 8.7 High / v3.1 7.5): an obsolete HTTP endpoint exposes the OAuth 2 client secret when the management plugin and OAuth settings are enabled, reachable without logging in; affected <3.13.15, 4.0.0-4.0.20, 4.1.0-4.1.11, 4.2.0-4.2.6; fixed 3.13.15/4.0.20/4.1.11/4.2.6; disclosed by Miggo Security alongside CVE-2026-57221; Nuclei template exists, EPSS ~2%, not on KEV; no confirmed in-the-wild exploitation found — [pentest-tools](https://pentest-tools.com/vulnerabilities-exploits/rabbitmq-management-oauth-2-client-secret-disclosure_29631); [OSV AZL-92334](https://osv.dev/vulnerability/AZL-92334); [INCIBE](https://www.incibe.es/index.php/en/incibe-cert/early-warning/vulnerabilities/cve-2026-57219); [threatcluster summary](https://threatcluster.io/cluster/hackers-can-exploit-rabbitmq-oauth-flaw-to-access-every-mess-bb779fee). #### NATS / JetStream
Authoritative guide: NATS "Securing NATS" chapter.
- Default: no authentication; "the bare server admits every connection", as does a server with no `authorization` block; keys: `authorization { users [ {user, password | nkey} ], token, timeout (default 2s), no_auth_user }`; `no_auth_user` admits unauthenticated connects as a named user; passwords may be bcrypt via `nats server passwd` — [NATS auth intro](https://docs.nats.io/running-a-nats-service/configuration/securing_nats/auth_intro)
- Model: accounts are isolated tenants (implicit global account `$G` when none configured); `$SYS` system account; auth methods: passwords, tokens, bearer JWTs, mTLS, NKeys; authorization = publish/subscribe subject grants, deny-by-default; operator mode trusts an operator public key with an account resolver; auth callout delegates to an external service — [NATS securing](https://docs.nats.io/running-a-nats-service/configuration/securing_nats)
- Monitoring endpoint (`http_port: 8222` or `-m 8222`, off until enabled) is unauthenticated by default; `/connz` exposes connection id, account, authenticated user, subscriptions; `/varz` server snapshot; `/routez`; `/jsz` JetStream streams/consumers; `/healthz` — [NATS monitoring](https://docs.nats.io/running-a-nats-service/nats_admin/monitoring)
- CVE-2025-30215 (CVSS 3.1 9.6 Critical; Mend v4 8.5): JetStream management API in `$JS` namespace lacked access checks, letting a user with JetStream management permission in one account act on assets in other accounts; at least one API can destroy data; no stream-content disclosure; affected 2.2.0 to <2.10.27 and <2.11.1; no workaround — [Wiz CVE DB](https://www.wiz.io/vulnerability-database/cve/cve-2025-30215); [Tenable](https://tenable.com/cve/CVE-2025-30215); [Mend](https://www.mend.io/vulnerability-database/CVE-2025-30215/)

#### Redis / Valkey (as broker and cache)
Authoritative guide: Redis security and ACL docs.
- Redis is "designed to be accessed by trusted clients inside trusted environments"; `bind 127.0.0.1`; protected mode (since 3.2.0) replies only to loopback when bound to all interfaces with no password; `requirepass` is legacy (now sets the default user's password); AUTH is sent unencrypted; `rename-command CONFIG ""` is deprecated in favor of ACLs; CONFIG can change `dir`/`dbfilename` to write RDB files to arbitrary paths (antirez's documented system-compromise vector); run as unprivileged user; TLS on client, replication, and cluster bus — [Redis security](https://redis.io/docs/latest/operate/oss_and_stack/management/security/)

## KQ2. Which signals require usage telemetry (consumer groups, connection lists, audit logs, cloud trails) vs config reads?

### Takeaway
Roughly half of the high-value checks are pure config reads (listener protocols, authorizer, ACL tables, IAM/resource policies, TLS settings, versions), but the differentiating checks — orphaned/over-privileged identities, actually-public-vs-policy-public, drift, and "who touches which topic" — require live telemetry from broker-native read-only endpoints (Kafka AdminClient metadata/ACLs/consumer groups, NATS `/connz`/`/jsz`, Redis `CLIENT LIST`/`ACL LOG`, RabbitMQ HTTP API) and from audit streams (Confluent audit-log topics, CloudTrail, Azure resource logs, GCP audit logs), most of which are off by default.

### Cited Findings
- Config-read evidence sources named in the sources: Kafka broker config reference keys (`listeners`, `auto.create.topics.enable`, `min.insync.replicas`, `sasl.enabled.mechanisms`, `connections.max.reauth.ms`, `remote.log.storage.system.enable`) — [Kafka 4.1 configs](https://kafka.apache.org/41/generated/kafka_config.html); RabbitMQ `rabbitmqctl list_users` / `list_permissions`, `rabbitmqadmin users list` / `users permissions`, `loopback_users`, `auth_backends.N` — [RabbitMQ access control](https://www.rabbitmq.com/docs/access-control); Redis `ACL LIST`, `ACL GETUSER`, `ACL CAT`, `bind`, `requirepass`, `aclfile` — [Redis ACL](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/); NATS `authorization`, `no_auth_user`, `accounts` — [NATS auth intro](https://docs.nats.io/running-a-nats-service/configuration/securing_nats/auth_intro); Pub/Sub `getIamPolicy` per topic/subscription/schema/snapshot — [Pub/Sub access control](https://docs.cloud.google.com/pubsub/docs/access-control); Schema Registry `listeners`, `authentication.method`, `inter.instance.protocol` — [Confluent SR security](https://docs.confluent.io/platform/current/schema-registry/security/index.html); HiveMQ `<tls-tcp-listener>`, extension inventory — [HiveMQ security](https://docs.hivemq.com/hivemq/latest/user-guide/security.html)
- Telemetry/runtime evidence sources: NATS `/connz` (connection id, account, authenticated user, subscriptions), `/varz` (live connections, slow consumers), `/jsz` (streams/consumers), unauthenticated by default once `http_port` is enabled — [NATS monitoring](https://docs.nats.io/running-a-nats-service/nats_admin/monitoring); MSK guidance to monitor total consumer-group count and delete unused groups (offsets retained until `offsets.retention.minutes`) — [MSK best practices](https://docs.aws.amazon.com/msk/latest/developerguide/bestpractices.html); Confluent Cloud audit logs cover Kafka AuthN/AuthZ, SR, ksqlDB, Flink, RBAC, SCIM, IP filters, connectors, networking — [Confluent Cloud audit methods](https://docs.confluent.io/cloud/current/monitoring/audit-logging/event-methods/index.html); Confluent Platform audit logs cover topic creation, ACL changes, user access and export failed-auth metrics to Prometheus — [Confluent Platform security](https://docs.confluent.io/platform/current/security/general-overview.html); Conduktor Gateway logs produce/fetch/admin activity ("70+ event types") — vendor claim — [Conduktor](https://conduktor.io/product/kafka-security)

- RabbitMQ permission caching means permission changes may only apply after reconnect — a config read can disagree with effective runtime state — [RabbitMQ access control](https://www.rabbitmq.com/docs/access-control)

### Inferences
- Config-only checks (agentless, read-once): listener protocol map, authorizer presence, super.users, ACL table, SR/Connect/UI auth settings, RabbitMQ users/permissions/tags, Redis ACL LIST + CONFIG GET, NATS config file, cloud resource policies/IAM/encryption/TLS-min/public-access flags, versions.
- Telemetry-required checks: (1) orphaned principals — ACL/user exists but no authentication event or active connection in N days (needs Kafka `describeConsumerGroups`/connection metrics, Confluent/CloudTrail/Azure/GCP auth events, NATS `/connz`, Redis `CLIENT LIST`, RabbitMQ `/api/connections`); (2) least-privilege recommendations — requires observed produce/consume per principal per topic (audit log or Gateway-level logs); (3) stale/empty consumer groups; (4) effective exposure — a listener bound to 0.0.0.0 is only "public" if reachable (EASM join, atlas #34); (5) secret-in-log detections (Kafka CVE-2026-33558, Pulsar CVE-2025-30677) need log inspection; (6) drift — requires periodic snapshots (atlas #56).
- Because RabbitMQ caches permissions and Kafka has had ACL-enforcement bugs, a best-in-class tool should distinguish "configured" from "effective" authorization and, where safe, verify effective access with a read-only probe (e.g., metadata request with an unauthenticated client on each listener).

### Gaps
- No source quantified default retention of Confluent Cloud audit logs or whether data-plane produce/consume events are included by default.
- No primary source on Kafka AdminClient methods (`describeAcls`, `describeConfigs`, `listConsumerGroups`, `describeCluster`) was fetched this session; their existence is standard Kafka API knowledge but is uncited here.
- No source on RabbitMQ HTTP API endpoints for connections/channels (`/api/connections`), only CLI listings.

## KQ3. What do buyers expect beyond checks: topology map, data-flow lineage, sensitive-topic classification, producer/consumer identity mapping, drift detection, ACL least-privilege recommendations, cost of misconfig?

### Takeaway
Vendor positioning in this space (Conduktor, Confluent, meshIQ) sells enforcement and governance features — proxy-level encryption/masking, RBAC/virtual clusters, audit export, schema-aware data quality, compliance framework mapping — rather than posture scoring; nothing fetched offers topology/lineage-driven risk, least-privilege recommendations from observed traffic, or drift detection as a named capability, and the incident record (Chattee Kafka leak, Kafdrop exposure, RediShell managed-service blast radius) argues that buyers most need "is my sensitive stream reachable, by whom, and did that change".

### Cited Findings
- Conduktor's product surface (vendor claims): field-level encryption, crypto-shredding, masking per consumer, group RBAC, virtual clusters/virtual ACLs with quotas, SSO, audit with SIEM export, CEL/SQL data-quality validation, Schema Registry proxy, compliance framework list; no mention of posture, drift, lineage, or secret detection — [Conduktor Kafka security](https://conduktor.io/product/kafka-security)
- Confluent Platform positions audit logs, RBAC, OAuth, mTLS, encryption, quotas, namespace isolation for connectors/SR, and Schema Registry-based masking/filtering for GDPR/PCI DSS — [Confluent Platform security](https://docs.confluent.io/platform/current/security/general-overview.html)
- Gravitee positions a Kafka Gateway with centralized ACLs and role-based policy across clusters; meshIQ positions monitoring of encryption status, authentication attempts, and ACL configurations with alerts — [Gravitee](https://gravitee.io/corpus/gen-1585/market-trend/kafka-security-posture.html); [meshIQ](https://www.meshiq.com/essential-kafka-security-best-practices-for-2024)
- The Chattee incident data (43M messages, 600k media, 400k users, purchase records, device identifiers/auth tokens per a secondary source) demonstrates the "sensitive topic reachable without auth" class — [Malwarebytes](https://www.malwarebytes.com/blog/news/2025/10/millions-of-very-private-chats-exposed-by-two-ai-companion-apps)
- The Kafdrop exposure demonstrated that stream contents carried cloud credentials and tokens, i.e., a broker leak is a credential leak — [Spectral](https://spectralops.io/blog/misconfigured-kafdrop-puts-companies-apache-kafka-completely-exposed/)
- RediShell affected managed services (ElastiCache, Memorystore, Azure Cache for Redis), and Wiz's guidance was to prioritize internet-facing instances — i.e., exposure-weighted CVE prioritization — [Wiz RediShell](https://wiz.io/blog/wiz-research-redis-rce-cve-2025-49844)
- Microsoft's baselines explicitly mark sensitive-data discovery/classification (DP-1) and DLP (DP-2) as "not supported" for Service Bus and Event Hubs — a gap a third-party tool could fill — [Service Bus baseline](https://learn.microsoft.com/en-us/security/benchmark/azure/baselines/service-bus-security-baseline); [Event Hubs baseline](https://learn.microsoft.com/en-us/security/benchmark/azure/baselines/event-hubs-security-baseline)
- Azure Event Hubs' `RootManageSharedAccessKey` root-style policy and SAS defaults, and SQS/SNS three-tier (admin/producer/consumer) access guidance, define the identity model buyers expect a tool to map — [Event Hubs baseline](https://learn.microsoft.com/en-us/security/benchmark/azure/baselines/event-hubs-security-baseline); [SQS best practices](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-security-best-practices.html)
- Pulsar's Function Worker CVEs (credential leak, RCE, file access) and Kafka Connect CVEs show that "extension/plugin" components are the recurring RCE path, so plugin/connector inventory is part of topology — [Pulsar security](https://pulsar.apache.org/security/); [Apache Kafka CVE list](https://kafka.apache.org/community/cve-list/)

### Inferences
- Expected "beyond checks" features, in buyer-priority order inferred from incidents and vendor positioning:
  1. Topology map: brokers, listeners (with protocol), controllers/ZooKeeper, Connect workers + connectors + plugins, Schema Registry, UIs (kafka-ui/Kafdrop/AKHQ), proxies/gateways (Conduktor, Gravitee), MirrorMaker/replicators, cloud namespaces/queues/topics/subscriptions, plus their network reachability. The atlas covers this partly via #32 attack-path graph and #34 EASM; the broker-specific graph (listener -> ACL -> principal -> topic -> consumer/sink) is beyond its headings.
  2. Data-flow lineage: topic -> connector/sink/subscription/Function -> downstream system (S3, DB, SaaS webhook), including SNS HTTP endpoints, EventBridge cross-account targets, Pub/Sub push endpoints; needed to answer "where does PII in topic X end up" and for data-residency (atlas #55).
  3. Sensitive-topic classification: sample messages with schema awareness (Avro/JSON/Protobuf via Schema Registry) to tag PII/PCI/secrets; this is DSPM at the integration layer (atlas #30) but no competitor fetched claims it for brokers; Azure explicitly lacks it.
  4. Producer/consumer identity mapping: principal -> topic -> role (producer/consumer/admin) from ACLs plus observed traffic; feeds NHI inventory (atlas #24) and orphan detection (#29).
  5. Drift detection: ACL/user/policy/listener diffs between snapshots; Datadog's "EventBridge rule disabled or deleted" and "Pub/Sub Subscriber modified" detections are the only drift-like items found and they are log-driven, not snapshot-driven.
  6. ACL least-privilege recommendations: generate minimal ACL/IAM from observed usage (requires KQ2 telemetry); no fetched competitor claims this for brokers.
  7. Cost/blast-radius of misconfig: tie an exposed unauthenticated listener to record counts/retention (e.g., Chattee-scale numbers), affected consumers, and whether topics contain secrets; expressed as "records exposed x sensitivity x reachability".
  8. Remediation artifacts: concrete config keys (e.g., `allow.everyone.if.no.acl.found=false`, `loopback_users`, `ACL SETUSER default off`, `aws:SecureTransport` deny statements, `disableLocalAuth`) and Terraform/IaC snippets (atlas #48/#50).
- Beyond the atlas headings: a broker-native topology/lineage graph, schema-aware sensitive-topic sampling, usage-derived least-privilege ACL generation, "configured vs effective" authorization verification, and plugin/connector/extension SBOM-style inventory are not explicit in the atlas and would be differentiators.

### Gaps
- No analyst report, buyer survey, or RFP checklist for broker-security tooling was found in this session; buyer expectations above are inferred from vendor positioning and incident write-ups, not from demand-side evidence.
- Confluent "Stream Governance"/lineage feature scope was not fetched; it may already offer topic-level lineage for Confluent Cloud, which would make lineage commodity there.

## KQ4. Which checks are genuinely unique (no current tool does them) vs commodity?

### Takeaway
Commodity = the cloud-API checks every CSPM already runs (MSK encryption/public/IAM/mTLS/version; SQS/SNS public-policy + SSE; Kinesis encryption; EventBridge bus policy; ElastiCache auth/encryption; Azure Policy for Service Bus/Event Hubs) plus vendor-native enforcement (Conduktor/Confluent RBAC, encryption, audit). Unique = anything that requires speaking the broker protocol or reading broker-internal state across heterogeneous fleets: ACL/least-privilege analysis, unauthenticated-listener probing, NATS monitoring-port and JetStream cross-account checks, Redis ACL-category analysis, kafka-ui/Jolokia/management-UI exposure, Connect/SR/plugin posture, version-to-CVE with exposure weighting, and all of GCP Pub/Sub and Azure messaging posture where Prowler has nothing.

### Cited Findings
- Commodity (already implemented): Prowler MSK x8, SQS x2, SNS x3, Kinesis x2, EventBridge x4 — [Prowler kafka](https://api.github.com/repos/prowler-cloud/prowler/contents/prowler/providers/aws/services/kafka); [sqs](https://api.github.com/repos/prowler-cloud/prowler/contents/prowler/providers/aws/services/sqs); [sns](https://api.github.com/repos/prowler-cloud/prowler/contents/prowler/providers/aws/services/sns); [kinesis](https://api.github.com/repos/prowler-cloud/prowler/contents/prowler/providers/aws/services/kinesis); [eventbridge](https://api.github.com/repos/prowler-cloud/prowler/contents/prowler/providers/aws/services/eventbridge). Datadog MSK x6, SQS x2, SNS x4, Kinesis x2, EventBridge x1, ElastiCache/MemoryDB ~13 — [Datadog default rules](https://docs.datadoghq.com/security/default_rules/)
- Not covered by Prowler at all: Azure Service Bus/Event Hubs/Event Grid and GCP Pub/Sub (no service directories) — [Prowler azure](https://api.github.com/repos/prowler-cloud/prowler/contents/prowler/providers/azure/services); [Prowler gcp](https://api.github.com/repos/prowler-cloud/prowler/contents/prowler/providers/gcp/services). - Exposure-weighted vulnerability prioritization is called for by Wiz's RediShell guidance (prioritize internet-facing) and by the ActiveMQ KEV history — [Wiz RediShell](https://wiz.io/blog/wiz-research-redis-rce-cve-2025-49844); [Help Net Security](https://www.helpnetsecurity.com/2023/11/02/cve-2023-46604-ransomware/)

### Inferences
- Unique / no fetched tool does them (candidate differentiators):
  1. Kafka ACL least-privilege and footgun analysis across self-managed/KRaft/MSK/Confluent/Redpanda: wildcard ACLs, `allow.everyone.if.no.acl.found`, super.users sprawl, principals with no auth activity, and version-aware "ACL semantics bugs" (CVE-2024-27309 migration window, CVE-2026-41115).

  3. Management-plane exposure for the ecosystem: kafka-ui/Kafdrop/AKHQ auth + version (<0.7.2), Connect REST auth, Schema Registry http/no-auth, RabbitMQ management + OAuth endpoint (CVE-2026-57219), ActiveMQ Jolokia/web console role mapping, EMQX dashboard/plugin-install keys, HiveMQ allow-all, NATS 8222.

- Commodity / do not differentiate on: MSK/SQS/SNS/Kinesis/EventBridge/ElastiCache encryption-public-IAM checks; per-vendor RBAC/encryption/masking enforcement (Conduktor/Confluent); generic CVE version matching without exposure context.
