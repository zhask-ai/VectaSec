## Key Question 1: What is the union of features across the leading NHI products, and which are table-stakes vs differentiator in 2026 analyst/buyer language?

### Takeaway
By October 2026 the independent NHI market has largely been absorbed: Astrix -> Cisco (May 2026), Entro -> SailPoint (closed June 29, 2026), Natoma -> Snowflake (announced May 27, 2026), Oasis -> Cyera (LOI July 28, 2026, reported closed Sept 2026), CyberArk/Venafi -> Palo Alto Networks "Idira". Table-stakes is now agentless discovery + inventory with owner/permissions/usage + risk scoring + stale/orphaned detection + one-click revoke/rotate + vault integration; differentiators are per-credential last-used telemetry, ITDR behavioral baselines, runtime enforcement/secretless access (Aembit, Silverfort), AI-agent control planes (Astrix ACP, Oasis AAM, Entro AAA, Okta/Entra), and ownership-discovery engines.

#### OWASP NHI Top 10 (2025) — buyer risk language
- The ten risks: NHI1 Improper Offboarding; NHI2 Secret Leakage; NHI3 Vulnerable Third-Party NHI; NHI4 Insecure Authentication; NHI5 Overprivileged NHI; NHI6 Insecure Cloud Deployment Configurations; NHI7 Long-Lived Secrets; NHI8 Environment Isolation; NHI9 NHI Reuse; NHI10 Human Use of NHI; ranked via OWASP Risk Rating Methodology — [OWASP project page](https://owasp.github.io/www-project-non-human-identities-top-10/2025); [CSA write-up](https://cloudsecurityalliance.org/articles/introducing-the-owasp-nhi-top-10-standardizing-non-human-identity-security)
- NHI1 prevention explicitly requires: offboarding workflow that reviews all NHIs tied to a departing employee, transfers ownership and rotates credentials they could access; HR-to-IAM automation; periodic recertification that every NHI is in use and has an owner; usage tracking/auditing. Defines three sub-cases: stale/dormant, orphaned (owner left), partially offboarded (non-owner with credential exposure) — [OWASP NHI1](https://owasp.github.io/www-project-non-human-identities-top-10/2025/1-improper-offboarding/)
- NHI7 mitigations: automated rotation, short-lived credentials that expire/refresh automatically (cites AWS/Azure), re-authentication for high-risk actions, least privilege; no specific rotation interval given — [OWASP NHI7](https://owasp.github.io/www-project-non-human-identities-top-10/2025/7-long-lived-secrets/)
- Publication date disputed: one glossary says January 2025, another vendor article September 2025 — [identra.ai](https://www.identra.ai/glossary/owasp-nhi-top-10/); [Doppler](https://www.doppler.com/blog/owasp-top-10-nhi-risks-2025)

### Inferences
- Table-stakes (every vendor claims, OWASP demands): agentless API-based discovery across cloud IAM, IdP, SaaS, vaults, code/CI; inventory tuple of identity -> credential(s) -> grant(s)/permissions -> owner -> consumers; risk score built from privilege x reachability x usage x hygiene findings; orphan/stale/over-privileged/long-lived/leaked flags; one-click revoke/rotate/decommission with ticketing/SOAR hooks; vault integration; SOC 2 Type II (all three leaders). Buyers map this to OWASP NHI1/2/5/7 and Gartner ISPM.
- Differentiators in 2026: (a) ownership-discovery engines with ML over logs/CMDB/free-text (Oasis, Entro lineage, Clutch lineage); (b) non-human ITDR with behavioral baselines and auto-revocation (Astrix, Entro, Clutch, Token, Silverfort runtime); (c) enforcement rather than observation — secretless brokers and proxies (Aembit, Silverfort RAP, Astrix ACP, Okta Agent Gateway); (d) agent control planes with per-agent identity, JIT scopes, and kill switch (Astrix ACP, Oasis AAM, Entro AAA, Okta, Entra blueprints); (e) secret-type breadth (Entro 1,200+ types) and in-vault governance (GitGuardian).
- The leaders' feature set is weighted toward cloud IAM + SaaS OAuth + vaults + code. Message brokers, API gateways, service meshes, and iPaaS appear mainly as secret *detectors* (Entro) or single connectors (Oasis lists Workato), not as first-class identity sources with usage telemetry.
- Analyst framing: Gartner now splits this across IVIP (visibility), ISPM (posture), ITDR (detection), plus emerging "AI Agent Security" and "Workload Identity Management"; a new product should position in ISPM/IVIP terms and map findings to OWASP NHI IDs.

## Key Question 2: Which telemetry sources give last-used for integration-layer principals, and which are structurally unavailable?

### Takeaway
Cloud IAM and IdPs expose first-class last-used APIs (AWS GetAccessKeyLastUsed and Service Last Accessed, Entra servicePrincipalSignInActivities and appCredentialSignInActivities, GCP Policy Analyzer activities.query, GitHub token_last_used_at, Okta token UI). Integration-layer systems (Kafka/Confluent, RabbitMQ, Redis, NATS, Istio, Kong) have no stored per-principal last-used field; last-used must be *derived* by continuously consuming audit/connection/metrics streams, several of which have short retention (Confluent 7 days) or record only denials (Redis ACL LOG, MSK authorizer logs).

### Cited Findings

#### Cloud IAM / IdP (first-class last-used)
- AWS `GetAccessKeyLastUsed` returns `LastUsedDate`, `ServiceName`, `Region` for an access key plus owning `UserName` — [AWS IAM API GetAccessKeyLastUsed](https://docs.aws.amazon.com/IAM/latest/APIReference/API_GetAccessKeyLastUsed.html)
- AWS `GenerateServiceLastAccessedDetails` (Access Advisor) is async (job ID), `Granularity` SERVICE_LEVEL (default) or ACTION_LEVEL; recent activity appears within ~4 hours; covers at least 400 days; includes all attempts not just successful calls (CloudTrail is authoritative for success/deny) — [AWS GenerateServiceLastAccessedDetails](https://docs.aws.amazon.com/goto/WebAPI/iam/GenerateServiceLastAccessedDetails); [AWS ServiceLastAccessed](https://docs.aws.amazon.com/IAM/latest/APIReference/API_ServiceLastAccessed.html)
- Entra "Service principal sign-in activity (preview)" gives last activity date per SP split by delegated/app-only and client/resource roles via `GET /beta/reports/servicePrincipalSignInActivities/{id}` (fields: delegatedClientSignInActivity, delegatedResourceSignInActivity, applicationAuthenticationClientSignInActivity, applicationAuthenticationResourceSignInActivity, lastSignInActivity with lastSignInDateTime/lastSignInRequestId). "Application credential activity (preview)" gives per-credential keyId, keyType (certificate/clientSecret), keyUsage, credentialOrigin, expirationDate, signInActivity.lastSignInDateTime via `GET /beta/reports/appCredentialSignInActivities/{id}`. Requires Entra ID P1/P2 and Reports Reader — [Entra usage and insights](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/concept-usage-insights-report)
- Entra sign-in logs include service principal and managed identity sign-in categories; default retention ~30 days, send to Log Analytics for longer (third-party guide) — [Entra sign-in logs](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/concept-sign-ins); [jjrmilner guide](https://jjrmilner.substack.com/p/20-basic-hygiene-foundation-mastering)
- GCP Policy Analyzer: `GET https://policyanalyzer.googleapis.com/v1/projects/{p}/locations/global/activityTypes/{serviceAccountLastAuthentication|serviceAccountKeyLastAuthentication}/activities:query`; role `roles/policyanalyzer.activityAnalysisViewer`; result includes `observationPeriod`; `lastAuthenticatedTime` always recorded as T07:00:00Z (day granularity); may omit very recent events; excludes API-key-bound requests and domain-wide delegation to Workspace (use Cloud Monitoring metrics); Pre-GA; service account insights flag 90-day unused — [GCP service account recent usage](https://docs.cloud.google.com/iam/docs/service-account-recent-usage)
- GitHub `GET /orgs/{org}/personal-access-tokens` returns `token_last_used_at`, `token_expires_at`, `token_expired`, `permissions` (organization/repository/other), `owner`, `access_granted_at`, `repository_selection`; filterable by last-used window; callable only by GitHub Apps; fine-grained PATs only (classic PATs not mentioned) — [GitHub REST PATs](https://docs.github.com/en/rest/orgs/personal-access-tokens)
- Okta: Security > API > Tokens shows status, type, name, creation, expiration, last-used; but System Log records only data-modifying API calls (PUT/POST/DELETE), so GET usage updates "last used" without a log event; last-used updates even if denied by network zone; tokens unused ~30 days are auto-revoked — [Okta support: last used](https://support.okta.com/help/s/article/information-about-api-token-creation-expiration-and-last-used-date); [Okta support: no logs](https://support.okta.com/help/s/article/okta-admin-dashboard-shows-recent-activity-for-an-api-token-but-there-are-no-corresponding-logs); [Okta support: find token activity](https://support.okta.com/help/s/article/how-to-find-api-tokens-activity-in-your-system-logs)

#### Integration layer (derived last-used only)
- Confluent Cloud: no documented last-used field for API keys. Audit log `kafka.Authentication` events record principal (service account) and the API key used; console filter by principal/subject/IP over max 7 days; audit topic `confluent-audit-log-events` retained 7 days on separate audit cluster, immutable; requires OrganizationAdmin and a Standard/Enterprise/Dedicated/Freight cluster; consuming requires an API key bound to the audit cluster; docs show a jq pipeline extracting API key IDs from auth events — [Confluent audit log configure](https://docs.confluent.io/cloud/current/access-management/audit-logging/configure.html); [Confluent audit log concepts](https://docs.confluent.io/cloud/current/monitoring/audit-logging/cloud-audit-log-concepts.html); [Confluent manage audit logs](https://docs.confluent.io/cloud/current/access-management/audit-logging/manage-audit-logs.html)
- Amazon MSK: IAM access control handles authn+authz; Kafka ACLs have no effect for IAM identities; "Authorizer Log Delivery" for Provisioned clusters (Standard and Express brokers) announced Aug 6, 2026 at no cost, delivering to CloudWatch Logs, S3, Data Firehose — captures each *denied* authorization request with client IP and API attempted (allowed requests not described) — [AWS What's New MSK authorizer logs](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-msk-kafka-authorizer-logs/); [MSK IAM access control](https://docs.aws.amazon.com/msk/latest/developerguide/iam-access-control.html)
- RabbitMQ: logs "user 'x' authenticated and granted access to vhost" at info, failed auth at warning (`user` log category); internal events `user.authentication.success` / `user.authentication.failure`; connection close entries include vhost and user; no per-user last-login tracking documented — [RabbitMQ logging](https://www.rabbitmq.com/docs/logging)
- Redis `ACL LOG` records only failures (auth failures and ACL denials) with username, age, and (since 7.2.0) timestamps; it does not record successful authentication; Upstash's ACL LOG always returns empty — [Redis ACL LOG](https://redis.io/docs/latest/commands/acl-log/); [Upstash ACL LOG](https://upstash.com/docs/redis/commands/server/acl-log)
- NATS: system account publishes `$SYS.ACCOUNT.<account>.CONNECT` and `.DISCONNECT` per client plus periodic STATSZ; requires connecting as a system user; message body fields not documented on that page; no stored last-used — [NATS sys accounts](https://docs.nats.io/running-a-nats-service/configuration/sys_accounts)
- Istio: `istio_requests_total` labels `source_principal` / `destination_principal` are set only when peer authentication (mTLS) is used; `source_workload` is `unknown` when source info is missing; `connection_security_policy` is `unknown` on source-side reports — [Istio metrics reference](https://istio.io/latest/docs/reference/config/metrics/)
- Entro treats Kafka, Confluent, RabbitMQ, Redis, MongoDB, Kong, Zapier, Apigee, Tyk, MQTT credentials as secret *types* (detection + validation), with no documented usage telemetry for them — [Entro supported secrets](https://documentation.sailpoint.com/entro/help/supported-secrets/index.html)
- Oasis lists Workato among supported platforms (listing-level claim only) — [AWS Marketplace Oasis](https://aws.amazon.com/marketplace/pp/prodview-blsgeikmunnxc)
- GitGuardian explicitly does not store last-used timestamps; "usage" is inferred from Secret Analyzer consumer/resource graphs — [GitGuardian discover your NHIs](https://docs.gitguardian.com/nhi-governance/discover-your-nhis)

### Inferences
- A three-tier telemetry model fits the evidence: Tier 1 "native last-used API" (AWS keys/roles, Entra SPs and credentials, GCP SAs/keys, GitHub fine-grained PATs, Okta tokens UI); Tier 2 "derivable from a streamed audit/connection log that must be continuously consumed and persisted by the NHI product" (Confluent auth events, RabbitMQ auth logs/events, NATS CONNECT events, Kafka authorizer logs when enabled, Istio per-principal request metrics via Prometheus); Tier 3 "structurally unavailable without additional instrumentation" (Redis successful auth — ACL LOG is failure-only; MSK IAM allowed calls — authorizer logs are deny-only per the announcement; Kong/iPaaS connections — undocumented here).
- Because Tier 2 sources have short retention (Confluent 7 days; NATS/RabbitMQ events are transient), an integration-layer NHI product must run its own collectors and persist a last-seen ledger per principal/credential — none of the leading NHI vendors document doing this for brokers/meshes.
- Precision caveats matter for staleness scoring: GCP rounds to a day (T07:00:00Z), AWS Access Advisor lags ~4h and counts failed attempts, Okta GET calls are invisible in System Log. A product should expose "confidence/precision" alongside last-used.

## Key Question 3: What does "NHI for AI agents" mean concretely?

### Takeaway
Concretely it means (1) an agent registry where each agent is a first-class directory object with a human owner/sponsor and a template/blueprint, (2) no long-lived credential on the agent itself (blueprint-held FIC/certs or broker-injected short-lived tokens), (3) delegated authority expressed as OAuth tokens where `sub` = user and the agent is the actor/client (`client_id`), with token exchange/transaction tokens for chaining, (4) gateways that mediate MCP tool access and log every tool call, and (5) a kill switch (Universal Logout / disable-all-of-blueprint). Standards (IETF WIMSE AIMS, draft-klrc-aiagent-auth, MCP OAuth 2.1) are informational drafts, not RFCs.

### Cited Findings
- IETF draft-ietf-wimse-aims (Sept 2026, Informational, WIMSE WG): defines AIMS as a conceptual model with eight components — Agent Identifiers, Agent Credentials, Credential Provisioning, Authentication, Authorization, Observability and Remediation, Policy, Compliance; each agent MUST have exactly one WIMSE identifier (may be a SPIFFE ID); credentials must bind to it, be short-lived with explicit expiry (X.509-SVID, WIT-SVID, JWT-SVID, WIT/WIC); "the LLM must never have access to agent credentials"; static API keys called an antipattern; user delegation via Authorization Code grant (passkey preferred) with agent authenticating using workload credentials not a client secret; own-behalf via Client Credentials or JWT Authorization Grant; `client_id` = agent, `sub` = delegated user per RFC 9068; Transaction Tokens between microservices; Token Exchange/identity chaining for cross-domain; CIBA for out-of-band human approval (local UI confirmation "not sufficient"); tamper-evident logs covering identity, delegated subject, resource, decision, posture, remediation — [draft-ietf-wimse-aims](https://datatracker.ietf.org/doc/html/draft-ietf-wimse-aims)
- draft-carleton-workload-authz-grant-00 (Aug 2026, individual, expires Feb 4 2027) profiles AIMS for agent platforms; its SPIFFE/WIMSE relationship section is still TODO — [datatracker](https://datatracker.ietf.org/doc/draft-carleton-workload-authz-grant/)
- CSA research note (Sept 2, 2026): no AI-agent-specific IETF draft has been adopted or reached Proposed Standard; stable building blocks are WIMSE architecture and OAuth 2.0 Token Exchange; draft-ni-wimse-ai-agent-identity-02 proposes dual-identity credentials binding agent identifier to owner (not adopted); draft-klrc-aiagent-auth-00 separates agent client identifier from delegated subject, recommends OpenID Shared Signals for revocation propagation; MCP June 2025 revision made OAuth 2.1 + Protected Resource Metadata (RFC 9728) + PKCE S256 baseline, Nov 2025 revision recommends OAuth Client ID Metadata Documents over Dynamic Client Registration; DAWN WG covers discovery only, not identity; advises verifying vendor token models match draft patterns rather than trusting the "agent identity" label — [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-ietf-agent-identity-standards-20260902-csa/)
- SPIFFE: short-lived SVIDs (X.509 and JWT) delivered via Workload API with automatic rotation; SPIRE provides attestation-based issuance (node and/or workload), SDS API, SPIFFE and OIDC federation, PKI integration, Kubernetes/VM/serverless support — [SPIFFE overview](https://spiffe.io/docs/latest/spiffe-about/overview/)
- Entra Agent ID: agent identity has no own credentials; blueprint holds FIC/certs/secrets and brokers tokens; sponsor field records accountable human/group; optional 1:1 agent user account for systems requiring a user; blueprint-scope Conditional Access, disable-all, revoke-grant-for-all; interactive agents get user tokens with subject=user, actor=agent identity; Copilot Studio agents auto-get agent identities with creator as sponsor; GA May 1, 2026 via Agent 365 — [Entra agent identities](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities); [What are agent identities](https://learn.microsoft.com/en-us/entra/agent-id/what-are-agent-identities); [CSA note](https://labs.cloudsecurityalliance.org/research/csa-research-note-ietf-agent-identity-standards-20260902-csa/)
- Okta for AI Agents (GA April 30, 2026): agent registration in Universal Directory with owner; shadow agent discovery with scopes and blast radius; Agent Gateway with virtual MCP server (coming soon); Privileged Credential Management (vaulted/rotated); Universal Logout for agents as kill switch; governance certifications for agents acting on behalf of users; SIEM export of tool calls and authorization decisions — [Okta showcase press release](https://www.okta.com/newsroom/press-releases/showcase-2026/)
- Aembit: MCP Identity Gateway (transparent proxy, agent never holds credentials), MCP Authorization Server (OAuth 2.1), blended user+agent identity per decision, attestation via AWS/Azure/K8s/OIDC/SPIFFE — [Aembit docs](https://docs.aembit.io/get-started/how-aembit-works/index.md); [Aembit AI agents](https://docs.aembit.io/get-started/use-cases/ai-agents/)
- Astrix Agent Control Plane: provisions agents with short-lived credentials, JIT access, scoped permissions, policy at creation; discovers managed/shadow agents and MCP servers; agentic threat detection for out-of-scope actions — [Astrix product](https://astrix.security/product/)
- Entro: shadow agent detection via endpoint scanning, SaaS APIs/audit logs, code/collab scanning; action-level policy intercepting unauthorized tool calls; "Agentic Access Administration" May 2026 — [SailPoint blog](https://www.sailpoint.com/blog/sailpoint-acquires-entro-security); [tech-insider.org](https://tech-insider.org/?p=22272)
- Oasis AAM launched Nov 2025 (vendor "first purpose-built" claim) — [tech-insider.org](https://tech-insider.org/?p=22272)
- Natoma/Okta listing references "Brokered Consent" and "Cross App Access" — [Okta Natoma listing](https://www.okta.com/integrations/natoma)
- Snowflake rationale for Natoma: identity-aware authorization, policies, and auditability for Cortex Agents connecting to enterprise systems via MCP — [No Jitter](https://www.nojitter.com/data-management/snowflake-acquires-natoma-to-expand-ai-agent-governance)
- Palo Alto Idira "Secure AI Agents": discovers active agents in SaaS/cloud/dev environments, adds ownership and permission context, time-limited access, audit trails — [Idira](https://www.paloaltonetworks.com/idira)

### Inferences
- Minimum viable "agent NHI" feature set for 2026 parity: agent object type with sponsor/owner, blueprint/template grouping, per-agent credential or broker binding, discovery of shadow agents from OAuth grants and SaaS audit logs, MCP server inventory, tool-call audit, scope/blast-radius view, kill switch, and certification campaigns. Standards alignment claims should cite WIMSE identifiers + OAuth token exchange, not "AIMS compliance" (there is nothing to be compliant with yet).
- For an integration-layer product the actionable hooks are: detect agents as *consumers* of broker/gateway credentials (e.g., an MCP server holding a Kafka API key or Redis ACL user), flag LLM-reachable long-lived secrets (AIMS antipattern), and attribute tool calls to delegated user + agent pairs where gateways expose that.
