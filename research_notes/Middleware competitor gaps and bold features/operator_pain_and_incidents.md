# Operator pain and real incidents in the integration layer (as of 23 Nov 2026)

Evidence labels used throughout:
- **[P]** = verified by me from a primary source I opened directly (vendor's own incident page, the original research post, or the official project blog).
- **[V]** = vendor-claimed (a company with a product to sell, or the affected vendor's own framing); not independently checked.
- **[T]** = third-party / secondary coverage (news, aggregator, CSA research notes, search-result summaries). I did not open the primary record. Check before quoting numbers.
- **[U]** = single-sourced or conflicting; treat as unverified.

Method note: about 40 searches and 6 full page reads. Reddit, Hacker News and Stack Overflow threads did not surface through the search tool, so there are almost no verbatim operator quotes from those forums in these notes. ## 1. What Kafka / RabbitMQ / NATS / Redis operators say is hard about security

### Takeaway
The broker enforces access but records nothing about ownership, purpose, usage or rotation, so the real jobs ("who owns this topic", "is this ACL still used", "can I rotate this without an outage") are done in Terraform, portals, spreadsheets or not at all. Unauthenticated brokers on the public internet are still measured in the hundreds of thousands (Jan 2026), and they leak live credentials and PII.

### Cited Findings
- **ACLs carry no ownership or lifecycle.** "ACLs enforce decisions; they do not create ownership, review cadence, rotation policy, naming discipline, or rollback procedure. Those pieces have to live in platform automation, Terraform, internal portals, or managed control planes." [V, AutoMQ blog, via search summary] — [AutoMQ](https://www.automq.com/blog/kafka-user-access-control-roles-acls-and-operational-boundaries)
- **No topic-to-owner map means access reviews stall.** "No ownership mapping means you can't answer 'who owns this topic?' If ownership is unclear, access reviews are impossible." Same source says cleanup fails because nobody documents which service account maps to which app, so permissions only accumulate. [V] — [Conduktor](https://www.conduktor.io/blog/kafka-security)
- **Wildcard/prefix ACLs silently widen.** Granting `topic-*` is easier than listing three topics; when the prefix grows from 10 to 100 topics the service reads data it should not. [V] — [Conduktor](https://www.conduktor.io/blog/kafka-security)
- **Shared credentials break attribution.** Service accounts are painful to provision and rotate so apps reuse them and engineers log in with app credentials; broker audit logs show principals, not people. [V] — [Conduktor security playbook](https://conduktor.io/blog/apache-kafka-security-playbook)
- **Dormant entitlements.** Recommended practice is periodic review to "revoke dormant consumer or producer rights" and a policy record tying each ACL to a business service, data classification and approved purpose — i.e. a record Kafka itself does not hold. [T] — [NHI Mgmt Group](https://nhimg.org/faq/why-do-kafka-acls-become-harder-to-manage-as-event-driven-architectures-expand/)
- **Rotation is a multi-step manual migration.** Amazon MSK's documented SCRAM rotation: create new user, configure the needed ACLs for it, wait for propagation, verify, then migrate clients. [T, AWS docs via search summary] — [AWS MSK docs](https://docs.aws.amazon.com/msk/latest/developerguide/msk-password-rotation.html)
- **Certificate rotation turns into outages.** A rotation plan that ignores ISR health, client retry behaviour, trust-store propagation or rolling-restart order "can turn a routine security change into a partial outage". [V] — [AutoMQ](https://www.automq.com/blog/tls-certificate-rotation-for-always-on-streaming-platforms). Clients that do not hot-reload keep presenting the old cert after rotation (documented for OTel Collector mTLS, same failure mode as Kafka clients). [T] — [OneUptime](https://oneuptime.com/blog/post/2026-02-06-fix-certificate-rotation-mtls-pod-restart/view). GitLab's runbook lists `x509: certificate has expired or is not yet valid` on reads of `__consumer_offsets` as a known Kafka symptom. [T] — [GitLab runbooks](https://runbooks.gitlab.com/product_analytics/ssl-troubleshooting/)
- **ZooKeeper to KRaft migration breaks on security metadata.** Confluent's known-issues: malformed ACLs (from user scripts or manual config; legacy ACLs missing the principal-type prefix, PREFIXED patterns containing wildcards) are migrated as-is and "can cause KRaft controllers to fail during startup, which may lead to cluster downtime"; a preflight tool `kafka-migration-check` exists for this. Stalls are commonly caused by super-user config (controller principal must be super user on brokers and vice versa). Cloudera: manual ACL changes during migration break it (NoAuthException). [T, vendor docs via search summary] — [Confluent known issues](https://docs.confluent.io/operator/current/co-migrate-kraft-known-issues.html); [Cloudera troubleshooting](https://docs.cloudera.com/cdp-private-cloud-base/7.3.2/kafka-kraft-migration/topics/kafka-troubleshoot-kraft-migration.html)
- **Unauthenticated message queues at internet scale (Censys ARC, 6 Jan 2026).** [P]
  - MQTT: 650,000+ hosts; 480,000+ (~74%) accept unauthenticated connections; 407,000 allow unauthenticated subscribe.
  - NATS: 48,809 hosts; 3,979 need no auth; 1,230 of those actively emitting events, with possible usernames, passwords, auth tokens and PII in topics.
  - ZeroMQ: 20,102 hosts; 9,491 unauthenticated PUB sockets.
  - Observed leaking on MQTT: real-time financial transactions, application logs with plaintext usernames and passwords, LTE signalling with geolocation and IMEIs.
  - Censys says affected organisations "may not know their services are reachable."
  — [Censys](https://censys.com/blog/unauth-mqueue-problem)
- **Redis.** Wiz (Oct 2025) estimated ~330,000 Redis instances exposed to the internet, ~60,000 with no authentication, when disclosing RediShell (CVE-2025-49844, CVSS 10, 13-year-old use-after-free in Lua; patched 3 Oct 2025). No in-the-wild exploitation was reported at disclosure. [T, Wiz research via coverage] — [Wiz](https://wiz.io/blog/wiz-research-redis-rce-cve-2025-49844); [SecurityWeek](https://www.securityweek.com/critical-vulnerability-puts-60000-redis-servers-at-risk-of-exploitation/)
- **RabbitMQ (July 2026).** Miggo disclosed flaws including CVE-2026-57219 (CVSS 8.7): an unauthenticated attacker can retrieve RabbitMQ's OAuth client secret with one HTTP request to the management interface. [T/U — CVE details from secondary coverage] — [CSO Online](https://www.csoonline.com/article/4196093/rabbitmq-flaws-expose-oauth-secrets-risk-complete-takeover-of-the-broker.html); [eSecurity Planet](https://www.esecurityplanet.com/threats/rabbitmq-vulnerabilities-could-enable-unauthenticated-broker-takeover/)
- **ActiveMQ (2026).** Shadowserver counted 6,476 internet-exposed instances at risk from actively exploited CVE-2026-34197. [T] — [SC World](https://www.scworld.com/brief/over-6400-apache-activemq-servers-at-risk-of-ongoing-attacks)
- **Brokers as attacker infrastructure.** A botnet seen in the 2026 Langflow exploitation wave used NATS for command and control. [T] — [CSA Langflow note](https://labs.cloudsecurityalliance.org/research/csa-research-note-langflow-sustained-exploitation-20260830-c/)

### Inferences
- The unsolved job is not "list ACLs" (`kafka-acls --list` does that) but "join ACLs to actual usage, an owner and a credential age". That needs ACL list + consumer-group/producer activity + principal-to-app map. This is the broker equivalent of cloud IAM "last accessed" analysis and I found no free or SMB-priced tool doing it across Kafka, RabbitMQ and NATS.
- A KRaft pre-flight for security metadata (malformed ACLs, missing prefixes, super-user gaps) exists only inside Confluent's commercial operator; open-source Kafka 3.x clusters heading to 4.x have no neutral equivalent that I found.
- Certificate and SASL credential expiry on brokers is a reliability incident first and a security incident second. A product that shows "this broker/client cert expires in N days and these clients will not hot-reload" sells to the on-call engineer, not only to security.
- Exposure of message buses is mostly accidental and unknown to the owner, which fits an outside-in scan with a DNS ownership gate.

### Gaps
- No verbatim r/apachekafka, r/rabbitmq or Confluent-forum complaints were retrievable; the pain statements above are mostly from vendors (Conduktor, AutoMQ) who sell the fix. Treat as directionally right but self-interested.
- No 2025-2026 count of internet-exposed Kafka brokers or RabbitMQ management UIs with default `guest` credentials was found.
- No public post-mortem of a Kafka outage caused specifically by mTLS/cert expiry was found; the failure mode is documented in runbooks, not incident reports.
- Nothing found on schema-registry / PII-in-topic governance pain with usable data.
- Multi-tenant isolation complaints (quotas, noisy neighbour, cross-tenant topic reads) not sourced.

## 2. What API gateway and service mesh operators say is hard

### Takeaway
The dominant 2025-2026 gateway story is ingress-nginx: a 9.8 unauthenticated RCE affecting ~43% of cloud environments (March 2025), then end of life on 24 March 2026 with no further security patches, forcing an annotation-by-annotation migration that teams describe as an application migration. Separately, API inventories are self-reported as complete but fewer than one in four teams know which APIs touch sensitive data.

### Cited Findings
- **IngressNightmare (24 Mar 2025).** CVE-2025-1974, CVSS 9.8, unauthenticated RCE via the ingress-nginx admission controller, giving access to all secrets across namespaces and cluster takeover. Wiz: ~43% of cloud environments vulnerable; 6,500+ clusters (including Fortune 500) exposing the admission controller publicly. Fixed in 1.12.1 / 1.11.5. Mitigation: network policy so only the API server reaches the admission webhook. [T, Wiz research via coverage] — [Wiz](https://wiz.io/blog/ingress-nginx-kubernetes-vulnerabilities); [Infosecurity](https://infosecurity-magazine.com/news/ingressnightmare-critical-bugs-40)
- **ingress-nginx retirement.** Announced 11 Nov 2025; best-effort maintenance until March 2026; repository archived 24 Mar 2026; no releases, bug fixes or security patches after. A Jan 2026 Steering/SRC statement called it critical infrastructure for about half of cloud-native environments. Existing deployments keep working unpatched. [T, official Kubernetes blog via search summary] — [Kubernetes blog](https://www.kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/); [Steering/SRC statement](https://www.kubernetes.io/blog/2026/01/29/ingress-nginx-statement/); [Google Open Source blog](https://opensource.googleblog.com/2026/02/the-end-of-an-era-transitioning-away-from-ingress-nginx.html)
- **The snippet annotations are both the security liability and the migration blocker.** The retirement notice names `snippets` annotations (arbitrary NGINX directives) as flexibility that became a liability. Traefik reports `configuration-snippet` and `server-snippet` were prevalent in its migration-tool data [V]. One guide: the more snippets you have, the more it is "an application migration—not just YAML changes" [T]. — [Kubernetes blog](https://www.kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/); [Traefik](https://traefik.io/blog/ingress-nginx-is-out)
- **End-user experience (CNCF, 2 Apr 2026).** [P] CERN: about 60% of its deployments still relied on ingress-nginx at end of 2025. Annotations mean "lock-in to specific controllers"; SSL redirection and proxy body size/buffering need documenting "to avoid surprises". Difficulty "depends on the deployment": own charts were easy, but many Ingress objects come from upstream chart dependencies that lack Gateway API support. Lesson: "Ensure some effort is left available to deal with events like this." A large tech company in the same post had relied on ingress-nginx for "bi-directional mTLS connections for zero-trust configurations", so those controls had to be re-created on the new controller. — [CNCF](https://www.cncf.io/blog/2026/04/02/ingress-nginx-retirement-experience-from-end-users/)
- **Annotation portability.** Google: if you rely on ingress-nginx annotations "you will likely have to migrate to another set of implementation-specific annotations". Vendors claim "80+" (Traefik) or "most" (F5) annotations map. [V] — [Google OSS blog](https://opensource.googleblog.com/2026/02/the-end-of-an-era-transitioning-away-from-ingress-nginx.html)
- **API inventory vs. data awareness (Akamai 2026 API Security Impact Study).** About three-quarters of respondents say they have a full API inventory; fewer than one in four know which APIs access sensitive data. Inventories are "static and incomplete" and miss shadow, rogue, zombie and deprecated APIs. [V, survey] — [Akamai](https://www.akamai.com/blog/security/2026/apr/api-weak-spot-study-ai-compounding-security-pressures)
- **Unknown APIs.** Imperva 2025 (via IBM): organisations have 10-20% more active APIs than they know about. [T] — [IBM](https://www.ibm.com/think/topics/api-sprawl). Salt 2025 figures (30-40% of footprint shadow/zombie; 15% strongly confident in inventory) appear only second-hand. [U] — [AppSecSanta](https://appsecsanta.com/research/api-security-statistics)
- **Kong.** Exposed Admin API (bound beyond localhost, no auth) is a long-standing, repeatedly documented misconfiguration. [T] — [Trend Micro case study](https://www.trendmicro.com/vinfo/hk/security/news/vulnerabilities-and-exploits/kong-api-gateway-misconfigurations-an-api-gateway-security-case-study). 2026 advisories: CVE-2026-14917, SAML plugin auth bypass when `validate_assertion_signature` is false [T, Kong advisory via search summary] — [Kong advisory](https://developer.konghq.com/support/security/security-advisory-cve-2026-14917/); CVE-2026-13341, indirect prompt injection in the Kong Konnect MCP server before 1.0.0 [T] — [OSV](https://osv.dev/vulnerability/CVE-2026-13341)
- **Istio.** Recurrent failure pattern in troubleshooting guides: PERMISSIVE mTLS left on (plaintext accepted silently); a namespace-level PeerAuthentication overriding mesh-wide STRICT; a DestinationRule disabling TLS between sidecar'd pods; policies spread over workload namespace, root namespace and all namespaces. `istioctl analyze` catches 40+ misconfiguration types. [T, single blog family] — [OneUptime](https://oneuptime.com/blog/post/2026-02-24-how-to-troubleshoot-istio-security-problems/view)
- **Expired gateway cert = full outage.** A published sev-1 post-mortem template describes an expired wildcard TLS certificate taking down an entire API gateway. [T, illustrative library entry, not a named company] — [grokdevops](https://grokdatum.github.io/grokdevops-wiki/library/postmortems/sev-1/expired-tls-cert-api-outage)

### Inferences
- After 24 Mar 2026 every unmigrated ingress-nginx cluster is running an unpatched, internet-facing component with a history of 9.8 RCEs. For a 0-3 person security team the jobs are: (1) do we still run it, where; (2) which Ingress objects use snippets or auth annotations; (3) after migration, did every route keep its auth, TLS redirect, rate limit and IP allowlist. Job 3 (security-equivalence diff across a controller migration) is not provided by any migration tool I found; ingress2gateway-style tools translate syntax, they do not prove auth parity.
- "Route with no auth plugin" and "mesh says STRICT but one namespace is PERMISSIVE" are the same class of problem: an effective-policy calculation across layered config. Operators debug it by hand with `istioctl` and `kubectl`.
- The Akamai gap (inventory yes, sensitivity no) suggests the saleable feature is "which routes reach PII-bearing upstreams and have weak auth", not another inventory.

### Gaps
- No sourced evidence for "plugin ordering causes auth bypass" in Kong or for decK/config drift incidents; searches returned nothing. It may be real but I cannot cite it.
- No hard data on how many clusters remained on ingress-nginx after March 2026, nor on any post-EOL ingress-nginx CVE.
- No independent report of specific behaviour differences that caused security regressions during ingress migration (e.g. lost auth-url, changed redirect semantics).
- No sourced material on gateway-vs-mesh policy drift or environment drift (staging vs prod) beyond general guidance.
- AWS API Gateway, Apigee and Azure APIM operator pain not covered by any retrieved source.

## 3. What teams running n8n, Zapier, Make, Workato, MuleSoft, Boomi or Airflow say is hard

### Takeaway
Automation platforms are credential vaults with code execution, and they are governed like personal productivity tools. The three structural pains are: automations outlive the people who built them, nobody can list what a credential or workflow can reach, and self-hosted instances (n8n especially) had a brutal 2026 of unauthenticated RCEs, malicious community nodes and leaked API tokens.

### Cited Findings
- **Offboarding does not stop automations.** "Account disablement no longer equals access removal": a workflow keeps running on credentials approved when its creator was trusted. [T] — [NHI Mgmt Group](https://nhimg.org/?p=81752)
- **Zapier: the account belongs to the person.** Third-party guide: the account "still belongs to the individual user, even if the user signed up with a company email address or has left your organization". Zapier's own transfer feature for business-critical Zaps is limited to Team owners and Company super admins/owners. [T + Zapier help centre via search summary] — [Zapier help](https://help.zapier.com/hc/en-us/articles/16534140057485-Safeguard-business-critical-Zap-workflows-when-a-team-member-transitions); [ConsultEvo](https://consultevo.com/zapier-manage-accounts-after-users-leave/)
- **The handover checklist is manual.** Guidance is to answer three questions per automation: what existed, who owns it now, what secrets or tokens does it use; and to look for hidden dependencies (notification to the builder's email, a step authenticated via a personal account, a scheduled job on the builder's machine). [T] — [PDQ](https://www.pdq.com/blog/it-automation-handover-checklist/)
- **n8n: workflow edit rights equal credential use rights.** A workflow runs with its own credentials, so "a shared workflow's editor can use every credential referenced in it". Credential sharing on self-hosted needs Business or Enterprise tier. [T] — [NHI Mgmt Group n8n guide](https://nhimg.org/n8n-security-guide); [n8n docs](https://docs.n8n.io/credentials/credential-sharing.md)
- **Credential-usage audit is a homemade job.** A community template exists purely to build an inventory mapping each workflow to the credentials it uses, exporting to Google Sheets, for self-hosted Docker users. [P-adjacent: n8n template listing via search summary] — [n8n template 14423](https://n8n.io/workflows/14423-audit-workflow-credential-usage-to-google-sheets-using-google-drive-and-sqlite3/). A forum thread asks "How do you handle API credentials in n8n workflows you share with teammates?" [T, title only] — [n8n community](https://community.n8n.io/t/how-do-you-handle-api-credentials-in-n8n-workflows-you-share-with-teammates/288743)
- **n8n community nodes are unaudited code with decrypted credentials.** Jan 2026 campaign: eight malicious npm packages posing as n8n integrations (one mimicking Google Ads) pulled OAuth tokens from the credential store, decrypted them with n8n's own master key and exfiltrated them; campaign still ongoing on 13 Jan 2026. npm packages are not audited before listing; n8n itself warns community nodes run with the same access as n8n. Mitigation: `N8N_COMMUNITY_PACKAGES_ENABLED=false`. [T, Endor Labs research via coverage] — [Endor Labs](https://www.endorlabs.com/learn/n8mare-on-auth-street-supply-chain-attack-targets-n8n-ecosystem); [The Hacker News](https://thehackernews.com/2026/01/n8n-supply-chain-attack-abuses.html)
- **n8n encryption key weakness.** GitGuardian: a human-memorable or predictable `N8N_ENCRYPTION_KEY` allows offline recovery of stored credentials; 13.8% of 31,793 Shodan-identified instances affected. [V/T] — [GitGuardian](https://blog.gitguardian.com/n8n-security-encryption-key-compromise/)
- **Leaked n8n API tokens (Aug 2026).** Tokens found in public GitHub commits, often next to the instance URL; a key committed months earlier stays usable until someone deletes or revokes it. [T] — [The Hacker News](https://thehackernews.com/2026/08/leaked-n8n-api-tokens-exposed-live.html)
- **Zapier platform issue (2026).** Token Security reported that code execution in "Code by Zapier" could extract credentials from memory; Zapier revoked the leaked token and tightened IAM roles, remediation confirmed by March 2026, published May 2026. [T/U] — via [search summary; primary not opened]. Separately Zapier told customers data "inadvertently copied to the repositories" may have been accessed after a 2FA misconfiguration on an employee account. [T; date not confirmed in retrieved text] — [TechRadar](https://www.techradar.com/pro/security/zapier-tells-customers-their-data-may-have-been-accessed)
- **Airflow.** Secrets leak through DAG code and Variables: Intezer (2021) found exposed instances leaking AWS, Slack, PayPal credentials, mostly hardcoded in DAG code. 2025-2026 CVEs repeat the class: CVE-2026-25219 (secrets masker missed `access_key` and `connection_string`, published 15 Apr 2026), CVE-2025-68675 (proxy credentials in task logs). [T; CVE dates from vulnerability databases, not Apache advisories] — [Intezer](https://intezer.com/?p=21394); [SentinelOne DB](https://www.sentinelone.com/vulnerability-database/cve-2026-25219/); [Wiz DB](https://www.wiz.io/vulnerability-database/cve/cve-2025-68675)
- **Scale of the secrets problem.** GitGuardian State of Secrets Sprawl 2026 (17 Mar 2026): ~28.65-29 million new hardcoded secrets on public GitHub in 2025, +34% year over year, the largest jump it has recorded; covers MCP configuration leaks. [V] — [GitGuardian](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/)
- **OWASP NHI Top 10 (2025)** ranks Improper Offboarding as NHI1. [T, OWASP project page via search summary] — [OWASP](https://owasp.org/projects/non-human-identities-top-10)

### Inferences
- "Leaver's automations" is a clean, unsolved, SMB-shaped job: on offboarding, list every workflow, connection, API key and webhook this person created or whose credential belongs to them, across Zapier/Make/n8n/Workato, and say what breaks if you revoke. Today it is a checklist item answered from memory.
- "Blast radius of one credential" (which workflows use it, what scopes it holds at the far end, when it was last rotated) is done by a community template writing to a Google Sheet. That is direct evidence of a spreadsheet-grade job.
- For self-hosted n8n, the 2026 pattern (see section 5) means a posture tool must treat the instance as a vault: version vs. KEV, public webhook/form endpoints, community nodes installed, encryption key strength, API tokens in git.

### Gaps
- No incident, research or operator complaint found for Workato, MuleSoft, Boomi or Make specifically in 2024-2026. Either quiet or not indexed; I cannot say which.
- No verbatim r/n8n, r/sysadmin or Zapier-community quotes retrieved.
- The "one-fifth of companies breached via former employee credentials" figure seen in a vendor blog has no traceable source; excluded.
- No data on citizen-developer sprawl volumes (workflows per employee, share built outside IT).
- Zapier repository incident date not confirmed from retrieved text (I believe it was disclosed in early 2025 but could not verify here).

## 4. What is hard about MCP servers, AI agents and AI gateways in production in 2026

### Takeaway
The AI integration layer repeated every mistake of the previous layers in eighteen months: no auth by default, example keys left in production, tool definitions that are executable trust, and integration platforms that hoard customers' OAuth tokens. By late 2026 there are KEV-listed bugs in an AI gateway (LiteLLM) and AI workflow builders (Langflow, n8n), a real breach of an agent integration platform (Composio), and measured exposure data.

### Cited Findings
- **Exposed MCP servers.** Trend Micro (Apr 2026 update): internet-exposed MCP servers grew from 492 (Jul 2025) to 1,467; 74% hosted on AWS/Azure/GCP/Oracle. Knostic: all 119 manually verified servers gave unauthenticated access to internal tool listings. [V/T] — [Trend Micro](https://www.trendmicro.com/vinfo/tr/security/news/vulnerabilities-and-exploits/update-on-exposed-mcp-servers-the-threat-widens-to-the-cloud)
- **MCP CVEs (selection).** CVE-2025-6514 mcp-remote, CVSS 9.6, client-side RCE when connecting to an untrusted server (JFrog); CVE-2026-33032 "MCPwn", CVSS 9.8, auth bypass in nginx-ui MCP server, actively exploited; CVE-2026-5058 aws-mcp-server command injection, 9.8; CVE-2026-23744 MCPJam Inspector listening on 0.0.0.0 with no auth; CVE-2025-68143/68144/68145 chain in Anthropic's mcp-server-git (Cyata). One count: 30+ MCP CVEs in a 60-day window in early 2026. [T; aggregator sources, verify against NVD] — [UpGuard incident list](https://upguard.com/blog/mcp-security-incidents); [CSA note](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-security-crisis-20260504-csa-styled/); [dev.to count](https://dev.to/ai_agent_digest/30-cves-in-60-days-mcps-security-reckoning-is-here-4p0n)
- **Tool poisoning is demonstrated, not theoretical.** Invariant Labs: hidden instructions in tool descriptions directed a model to steal SSH keys; WhatsApp MCP server shown exfiltrating chat histories; variants are direct poisoning, tool shadowing and rug pulls. Microsoft warned (June 2026) that poisoned MCP tool descriptions can make agents leak data. [T] — [HOL](https://hol.org/blog/mcp-tool-poisoning-ai-agent-protocol-attack-surface); [UpGuard](https://upguard.com/blog/mcp-security-incidents)
- **Prompt-injection exfiltration through connectors (research/PoC, with dates).** GitHub MCP via malicious issue leaking private repos (Invariant, May 2025); Supabase MCP via Cursor (Jul 2025); Atlassian MCP (Jun 2025); "GrafanaGhost" zero-click exfiltration via Grafana's AI assistant (Noma, Apr 2026); "Agentjacking" via Sentry MCP injection into coding agents (CSA note, Jun 2026); ChatGPT Gmail connector PoC (reported Sep 2026). [T; these are researcher demonstrations, not confirmed customer breaches] — [UpGuard](https://www.upguard.com/blog/ai-github-agents-issue-leaked-private-repos); [Simon Willison](https://simonwillison.net/2025/Jun/19/atlassian-prompt-injection-mcp); [CSA Agentjacking](https://labs.cloudsecurityalliance.org/research/csa-research-note-agentjacking-mcp-sentry-injection-2026/)
- **Shadow MCP on laptops.** Snyk (telemetry from ~10,000 developer environments): 1 in 12 developers with MCP servers has a HIGH or CRITICAL finding, including confirmed prompt injection in tool descriptions. Tenable 2026: 70% of enterprises have at least one AI/MCP package in production and almost none have a formal inventory or approval process. Stacklok: questionnaires and periodic audits are the default discovery method and miss what developers add constantly. Qualys calls MCP servers "the new shadow IT for AI". [V, all vendors selling the fix] — [Snyk](https://snyk.io/lp/state-of-agentic-dev-supply-chain-report/); [Stacklok](https://stacklok.com/resources/shadow-mcp-how-to-find-rogue-mcp-servers-before-they-find-you/); [Qualys](https://blog.qualys.com/product-tech/2026/03/19/mcp-servers-shadow-it-ai-qualys-totalai-2026)
- **Shadow servers inherit the developer's credentials**: a local MCP server uses the cloud credentials file the developer already has, so it gets what the developer can touch, not what the task needs. [V] — [Obot](https://obot.ai/blog/shadow-mcp-servers)
- **LiteLLM gateways: one in ten wide open (Wiz, published 9 Sep 2026).** [P] Of 3,074 internet-facing instances scanned in Feb 2026, 294 (9.6%) accepted the default master key and 191 (6.2%) required no authentication. "As of today, the master key is still set by default to `sk-1234`." With the key: every configured provider API key (LLMjacking), forged user sessions (master key signs session JWTs), MCP tool execution with arbitrary arguments, effectively pre-auth root RCE before v1.82.0, and IAM credential theft via pass-through endpoints reaching the metadata service (header forwarding defeats IMDSv2). CVE-2026-59822 (MCP auth bypass: any Bearer token creates a session) was added to CISA KEV; Wiz saw exploitation in its honeypot on 7 Jul 2026. Pass-through endpoint abuse was not fixed because LiteLLM treats admins as trusted. — [Wiz](https://www.wiz.io/blog/off-guard-breaking-litellm-from-authentication-bypass-to-cloud-compromise). Note: secondary coverage splits the 294 as 191 no-key + 103 `sk-1234`, which conflicts with the Wiz page's "294 accepted default, 191 no auth" phrasing. — [The Hacker News](https://thehackernews.com/2026/09/nearly-1-in-10-exposed-litellm-gateways.html)
- **Agent integration platforms hoard OAuth tokens.** Composio (May 2026, section 5) and Context.ai/Vercel (Apr 2026) are both cases where a platform holding customers' tokens was the breach. Commentary names it "the OAuth hoarding problem". [T] — [Arcade](https://www.arcade.dev/blog/vercel-contextai-and-the-oauth-hoarding-problem)
- **"Allow All" scopes.** Context.ai said at least one Vercel employee signed up with their enterprise account and granted "Allow All" permissions on Google Workspace. [T] — [The Register](https://www.theregister.com/2026/04/20/vercel_context_ai_security_incident/)
- **AI workflow builders hold provider keys.** In the Langflow CVE-2026-33017 campaign attackers exfiltrated environment variables and captured OpenAI, Anthropic and AWS keys plus database strings. [T] — [CSO Online](https://www.csoonline.com/article/4151203/attackers-exploit-critical-langflow-rce-within-hours-as-cisa-sounds-alarm.html)

### Inferences
- An AI gateway is the single highest-value object in a small company's AI stack: one key unlocks all provider keys, all connected MCP tools and often the cloud role. "Is my LiteLLM/Portkey reachable, on a default key, on a KEV version, with pass-through to the metadata service" is a five-check posture job with measured prevalence (9.6%).
- MCP inventory is being done by questionnaire. An agentless product cannot see laptops, but it can see the server side: which OAuth grants, API keys and tokens in the company's SaaS and cloud accounts were issued to MCP servers, agent platforms (Composio-class) and AI tools, with what scopes, and when last used. That reframes "shadow MCP" as "shadow grants", which is discoverable without an endpoint agent.
- Tool-definition drift (rug pull) is a posture-diffable artefact: hash the tool descriptions of approved servers and alert on change.
- The "third-party holds my tokens" pattern means a customer needs a per-vendor kill list: if vendor X is breached, here are the grants, keys and connections to revoke, in order. Composio's customers had to do this by hand under a deadline (section 5).

### Gaps
- No confirmed, named customer breach caused purely by MCP tool poisoning or prompt injection through a connector was found; evidence is researcher demonstrations plus the Composio chain (malicious tool definitions registered by an attacker who already had a foothold).
- Portkey: no incident or exposure research found.
- OWASP Top 10 for LLM / agentic applications not retrieved; no citations from it here.
- Shadow-MCP prevalence numbers come only from vendors; the "15% of employees run two MCP servers" stat has no traceable origin and is excluded.
- EchoLeak (M365 Copilot, 2025) and Asana MCP data exposure (2025) were not returned by search and are not cited.

## 5. Breaches and incidents 2024 to Nov 2026 that started in or moved through the integration layer

### Takeaway
Three incident families dominate: (a) stolen OAuth tokens held by an integration vendor used to bulk-read customers' SaaS data (Drift, Gainsight, Context.ai/Vercel, Composio, Klue, ConnectWise: six in fifteen months); (b) unauthenticated RCE in internet-facing integration software holding credentials (MFT products, ingress-nginx, n8n, Langflow, LiteLLM); (c) supply-chain poisoning of integration components (LiteLLM on PyPI, n8n community nodes). In nearly every case the customer-side control that would have limited damage was the same short list: know the grant exists, scope it narrowly, restrict it by IP, expire it, and watch its API volume.

### Inferences
- Family A is a repeatable pattern with six instances; CSA explicitly groups Salesloft, Gainsight, Klue and ConnectWise. The customer never "got hacked" in the usual sense; a grant they had forgotten about was used as designed. The preventive controls are all posture facts readable through SaaS admin APIs without an agent: grant exists, scope breadth, IP restriction, token age, last use, API volume baseline.
- Family B victims are disproportionately small self-hosters (n8n, Langflow, LiteLLM run by one engineer). Time from disclosure to exploitation was ~20 hours for Langflow. A weekly scan is too slow; the useful feature is "you run X version Y, it entered KEV today, it is internet-reachable, here is what it holds".
- The second-order damage is the secrets inside the integration system. GTIG says the Drift actor's "primary intent" was harvesting credentials from Salesforce case text. A "what secrets would an attacker find inside this system" check (support cases, workflow definitions, env vars, DAG variables) directly addresses the pivot.
- Vendor-breach response is a job nobody has tooling for: Composio customers were told to rotate keys by a deadline, enable IP allowlists, ask their own end-users to revoke API-key connections Composio could not revoke, and review each provider's audit logs for 24 IOC IPs.

## 6. What post-mortems say about detection time and why existing tools missed it

### Takeaway
Detection was slow or external in most of these cases, and the stated reason is consistent: integration identities are trusted and barely monitored, vendor-side detection saw the infrastructure intrusion but not the token theft, and the logs that would show abuse sit in the victim's SaaS tenant where nobody looks.

### Cited Findings
- **Integration identities are under-monitored.** ReliaQuest on Klue: integration identities "are typically monitored far less closely than employee accounts"; "a 24-hour automated query loop could run from a 'trusted' integration account without tripping the usual alarms"; nearly 1,000 queries in 15 minutes in one environment; "a legitimate integration's own credentials were used to quietly siphon CRM records at scale". [P] — [ReliaQuest](https://reliaquest.com/blog/threat-spotlight-integration-abused-in-crm-data-theft)
- **Password reset does not end access.** "Revoking the refresh token, not just resetting a password, is what severs persistent access." [P] — [ReliaQuest](https://reliaquest.com/blog/threat-spotlight-integration-abused-in-crm-data-theft)
- **Drift: five months from first access to exfiltration, ten days of exfiltration.** Reconnaissance in Salesloft/Drift environments March-June 2025; bulk export 8-18 Aug 2025; revocation 20 Aug. The actor deleted query jobs, "however logs were not impacted" — evidence existed in Salesforce Event Monitoring (UniqueQuery events) for those who had it and looked. [P for Aug dates and log statement; T for March-June] — [GTIG](https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift); [TechCrunch](https://techcrunch.com/2025/09/08/salesloft-says-drift-customer-data-thefts-linked-to-march-github-account-hack/)
- **Vendor saw the intrusion, missed the token theft.** Context.ai detected and stopped unauthorised access to its AWS environment in March 2026, but OAuth token exfiltration was not identified until Vercel's investigation in April. Nudge Security says the compromise was visible in threat intel for weeks before Vercel was hit. VentureBeat headline: the breach "exposes the OAuth gap most security teams cannot detect, scope or contain". [T] — [Trend Micro](https://trendmicro.com/en_us/research/26/d/vercel-breach-oauth-supply-chain.html); [Nudge Security](https://www.nudgesecurity.com/post/the-vercel-breach-what-to-do-in-the-next-24-hours); [VentureBeat](https://venturebeat.com/security/vercel-breach-exposes-the-oauth-gap-most-security-teams-cannot-detect-scope-or-contain)
- **Tokens lived for years.** Gainsight: tokens in use dated from Oct 2017 to Aug 2023, i.e. 2-8 years old at time of abuse; the company cannot determine how they were first exposed. [V/T] — [Gainsight CTO](https://unchurned.gainsight.com/p/when-oauth-tokens-live-too-long-and). Snowflake: infostealer-harvested credentials "were still valid, in some cases years after they were stolen". [T] — [Google/Mandiant](https://cloud.google.com/blog/topics/threat-intelligence/unc5537-snowflake-data-theft-extortion)
- **Stale test credential.** Klue entry was via "an old, unused testing credential that was still somehow active" (Huntress via coverage). [T] — [BleepingComputer](https://bleepingcomputer.com/news/security/klue-oauth-breach-linked-to-icarus-salesforce-data-theft-attacks)
- **Mass revocation destroys evidence.** After Gainsight, commentators noted Salesforce's blanket revocation removed the records customers needed to work out which users had granted OAuth access. [T] — [Oasis](https://www.oasis.security/blog/gainsight-salesforce-oauth-incident)
- **Vendor cannot fully revoke for you.** Composio could revoke OAuth tokens across ~100 toolkits but not API-key connections ("under 5%" unrevocable); customers' end-users had to rotate at each provider. Its page does not state how the intrusion was detected or the dwell time. [P] — [Composio](https://composio.dev/blog/composio-may-2026-security-incident)
- **Exploit-to-patch gap.** GoAnywhere exploited from 11 Sep 2025, advisory 18 Sep (7 days of zero-day use). Langflow exploited ~20 hours after disclosure. n8n: 24,700+ instances still unpatched roughly a month after Ni8mare. [T] — [The Hacker News](https://thehackernews.com/2025/10/from-detection-to-patch-fortra-reveals.html); [CSO Online](https://www.csoonline.com/article/4151203/attackers-exploit-critical-langflow-rce-within-hours-as-cisa-sounds-alarm.html); [The Register](https://www.theregister.com/2026/03/12/cisa_n8n_rce/)
- **Owners do not know they are exposed.** Censys on open message queues: affected organisations "may not know their services are reachable". [P] — [Censys](https://censys.com/blog/unauth-mqueue-problem)
- **Survey claim.** 85% of organisations lack full visibility into third-party vendors connected via OAuth apps. [U — cited by NHI Mgmt Group from an unnamed separate survey] — [NHI Mgmt Group](https://nhimg.org/articles/2026-dbir-shows-credential-abuse-and-ai-risk-still-drive-breaches/)

### Inferences
- Why CSPM/EDR/SIEM missed these: the abused object is a legitimate grant on a SaaS control plane, used from the vendor's or attacker's infrastructure, never touching an endpoint or the customer's cloud account. CSPM does not model it; EDR cannot see it; SIEM only helps if the SaaS audit log is licensed, ingested and has a rule.
- For a 0-3 person team, behavioural detection on SaaS API logs is unrealistic. Posture reduces exposure without a SOC: IP-restrict the grant, narrow the scope, expire the token, remove the unused one. Each of the six family-A incidents would have been blunted by IP restriction alone, which GTIG and ReliaQuest both recommend.
- A cheap detective control that fits a posture product: a daily "integration identity API volume vs. its own 30-day baseline" number per connected app. It needs one log source per SaaS and no rule-writing.

### Gaps
- No formal root-cause report from Vercel, Klue or ConnectWise was retrieved; detection narratives are from responders and press.
- Mandiant M-Trends 2026 dwell-time figures not retrieved.
- No post-mortem found that names a specific security product and explains why it missed the activity; "tools missed it" is researcher commentary.

Tenable: almost no enterprise has a formal inventory or approval process for AI/MCP packages. — via [Qualys/Tenable coverage](https://blog.qualys.com/product-tech/2026/03/19/mcp-servers-shadow-it-ai-qualys-totalai-2026) [V]
- **Ingress migration audit: kubectl one-liners.** Practitioner advice is to inventory Ingress objects, annotations and snippet usage with `kubectl get ingress -A` queries, then test in parallel. — [dev.to playbook](https://dev.to/onin/the-end-of-kubernetesingress-nginx-your-march-2026-migration-playbook-fhn); [AWS guide](https://aws.amazon.com/blogs/networking-and-content-delivery/navigating-the-nginx-ingress-retirement-a-practical-guide-to-migration-on-aws) [T]
- **Kafka ACL ownership and review: Terraform, portals, "an internal portal".** — [AutoMQ](https://www.automq.com/blog/kafka-user-access-control-roles-acls-and-operational-boundaries) [V]. Quarterly manual review is the recommended cadence. — [Conduktor](https://www.conduktor.io/blog/kafka-security) [V]
- **Vendor-breach response: manual log hunts.** Search each integrated app for published IOC IPs and user agents; open a Salesforce support case to obtain the actor's queries; grep Salesforce objects for `AKIA`, `snowflakecomputing.com`, `password`, `secret`; run Trufflehog. — [GTIG](https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift) [P]. Check GitHub audit logs for a specific 8-hour window and 24 IPs. — [Composio](https://composio.dev/blog/composio-may-2026-security-incident) [P]
- **Istio effective policy: by hand.** Check workload namespace, root namespace and all namespaces; temporarily add a permissive policy to confirm cause. — [OneUptime](https://oneuptime.com/blog/post/2026-02-24-how-to-debug-why-authorization-policy-is-blocking-traffic/view) [T]
- **API sensitivity mapping: not done.** Fewer than one in four know which APIs access sensitive data. — [Akamai](https://www.akamai.com/blog/security/2026/apr/api-weak-spot-study-ai-compounding-security-pressures) [V]

### Inferences
- Each of these has the same shape: a join across two systems that neither system performs (workflow x credential, person x automation, grant x scope x usage, ACL x traffic, Ingress x auth annotation). A product whose core is that join, rather than per-system config linting, is differentiated from the misconfiguration-checklist approach.

### Gaps
- No direct survey quantifying how many SMBs track integrations in spreadsheets.
- No first-hand operator testimony retrieved; evidence is the existence of the manual artefacts and guides.

## Ranked list: the most painful unsolved jobs (synthesis)

### Takeaway
Ranked by (incident evidence 2025-2026) x (lack of existing tooling at SMB price) x (fit for an agentless posture product). Items 1-6 each map to at least one named breach above.

### Cited Findings
All evidence for the ranking is cited in sections 1-7; pointers are given per item.

### Inferences
1. **"Which third parties hold tokens into my SaaS, with what scope, how old, IP-restricted or not, last used when."** Six breaches in 15 months (Drift, Gainsight, Context.ai/Vercel, Composio, Klue, ConnectWise). Controls named by GTIG and ReliaQuest are all posture facts. Sections 5A, 6.
2. **"Vendor X was just breached: what do I revoke, rotate and check, in what order."** A per-vendor kill list and IOC log sweep. Done by hand under deadline in Composio and Drift. Sections 5A, 7.
3. **"Is my self-hosted integration tool (n8n, Langflow, LiteLLM, MFT) internet-reachable, on a KEV version, and what credentials does it hold."** Exploited within ~20 hours; 24,700 n8n instances unpatched a month on; 9.6% of LiteLLM gateways open. Sections 3, 4, 5B.
4. **"A person left: which automations, connections, API keys and webhooks are theirs, and what breaks if I revoke."** OWASP NHI1; Zapier accounts belong to the individual; handled by checklist. Sections 3, 7.
5. **"What can this one credential reach, and which workflows use it" (credential blast radius).** n8n editor rights equal credential rights; community Google-Sheets template is the tooling. Sections 3, 7.
6. **"Stale and long-lived tokens and test credentials": find grants and keys unused for N days or older than N months and retire them.** Gainsight tokens 2-8 years old; Klue test credential; Snowflake credentials valid years after theft. Sections 5A, 6.
7. **"Is my AI gateway on a default or missing master key, and does it expose provider keys, MCP tools or the cloud metadata service."** Measured prevalence, KEV entry, real intrusion. Section 4.
8. **"After leaving ingress-nginx, did every route keep its auth, TLS, rate limit and allowlist" (security-equivalence diff), and "am I still running the retired controller".** EOL 24 Mar 2026; snippets are the blocker; no parity tooling found. Section 2.
9. **"What secrets are sitting inside my integration systems" (support cases, workflow JSON, env vars, Airflow Variables, DAG code).** The Drift actor's stated primary intent; Langflow env-var theft; Airflow CVEs. Sections 3, 5.
10. **"Which unapproved plugins, community nodes and package versions are in my automation and AI gateway stack."** n8n npm campaign; LiteLLM PyPI twice. Sections 3, 5C.
11. **"Which AI agents, MCP servers and agent platforms have grants into my accounts" (server-side shadow-MCP discovery).** Inventory by questionnaire today. Section 4.
12. **"Is any broker, queue or cache of mine reachable without auth, and is it leaking data right now."** 480k MQTT, 3,979 NATS, ~60k Redis; owners unaware. Section 1.
13. **"Which Kafka/RabbitMQ ACLs are unused, wildcarded or ownerless" (ACL x actual usage x owner).** Vendor-evidenced pain; no cross-broker SMB tool found. Section 1.
14. **"Which certificates and SASL/API credentials on brokers, gateways and meshes expire soon, and which clients will not hot-reload."** Outage-driven; sells to on-call. Sections 1, 2.
15. **"Rotate this broker or integration credential without an outage": a guided dual-credential rotation with verification.** MSK's manual multi-step; AutoMQ's outage warning. Section 1.
16. **"Integration identity API volume vs. its own baseline" as a zero-rule detective signal.** Klue ran ~24h unnoticed; ~1,000 queries in 15 minutes. Section 6.
17. **"Effective policy" across layers: route with no auth at the gateway, namespace PERMISSIVE under mesh STRICT, DestinationRule disabling TLS.** Hand-debugged today. Section 2.
18. **"Which public webhook, form and 'public flow' endpoints exist on my automation tools, and are they authenticated."** Precondition for Ni8mare and Langflow CVE-2026-33017. Sections 3, 5B.
19. **"Which APIs/routes reach sensitive data and have weak auth."** Three-quarters have an inventory, under a quarter know sensitivity. Section 2.
20. **"Is my Kafka security metadata safe to migrate to KRaft" (malformed ACLs, missing prefixes, super-user gaps) pre-flight.** Only in a commercial operator. Section 1.
21. **"Have my approved MCP servers' tool definitions changed" (rug-pull diff).** Demonstrated attack class; simple hash-pin control. Section 4.
