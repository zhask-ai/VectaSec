## 1. Agentic security: what autonomous remediation and investigation agents actually do, and their guardrails

### Takeaway
Shipped "remediation agents" in 2026 mostly investigate, give a verdict with a confidence score, generate a fix (CLI/Terraform/PR) and hand it to a human or a coding agent; direct execution exists but sits in preview, behind templates, per-task permission levels, and reversibility promises. The common guardrail pattern is: graded autonomy levels, agent-own identity capped at the creator's rights, full step traces, human approval for anything that changes state, and a proof-the-fix-worked step.

### Cited Findings
- **C1. Root-cause + verdict + fix agent (Wiz Green Agent).** Preview (public preview; announced 2026-03-26). Traces an issue across cloud resources, IAM, network paths and code commits; outputs a Remediate/Ignore verdict with confidence score and suggested severity change; identifies the owner; generates CLI/Terraform/Kubernetes fixes; one-click PR or hand-off to a coding agent; also exposed via API and MCP. Guardrails: availability-affecting steps marked Suggested/Optional, restore instructions included, "contain before fix" advice; learns from previously ignored issues. No explicit approval workflow, no post-fix verification, no metrics, no customer quotes on the page. [P] — [Wiz](https://www.wiz.io/blog/introducing-wiz-green-agent)
- **C2. One-click execution of response actions in the customer cloud + workflow chaining (Wiz Remediation and Response; Wiz Workflows).** Remediation and Response: Preview (public preview, 2026-08-04). Workflows: GA. Actions come from pre-built templates; Workflows chains agents, actions and integrations into repeatable multi-step processes. [P] — [Wiz at Black Hat 2026](https://www.wiz.io/blog/wiz-at-black-hat-2026)
- **C3. Kafka-native task agents with four autonomy levels (Conduktor Agents).** Launched 2026-11-04, free in Console, "GA" not stated; bring-your-own model (Claude, OpenAI, Bedrock). Built-in security agents: over-broad or unclaimed access with a tighter grant suggested, certificates near expiry, most valuable topics and their readers; plus unowned topics, stale consumer groups, risky schema changes. Triggers: schedule, Kafka event (topic/subject/group/connector created/changed/deleted), or on request. Each task has one level: Report / Recommendation / Approval / Automation (automation only in admin-permitted custom tasks). Guardrails: agents created disabled; "Run once" preview; each agent has its own "agent identity"; never more permissions than its creator, checked on every call; per-task MCP tool subset; caps on model calls, tool calls, tokens, duration; loop detection; quiet period and max runs/hour; every model turn and tool call traced (sample trace: 33 steps, 14 tool calls, 5,337 tokens). No customer evidence yet. [P] — [Conduktor](https://www.conduktor.io/blog/conduktor-agents)
- **C4. Trigger- and confidence-threshold-driven remediation with selectable human review (Cycode Agentic Workflows).** Preview (early access, Aug 2026). Agents triage/remediate on configured triggers and confidence thresholds; customer chooses which actions need human review. [S] — [SecurityWeek BH part 1](https://www.securityweek.com/black-hat-usa-2026-summary-of-vendor-announcements-part-1/)
- **C5. "Governed closed-loop response": act within team-set limits, every action traceable and reversible (SentinelOne Purple AI).** Announced; GA "expected later this quarter" as of Aug 2026 (current status not confirmed). ### Inferences
- VectaSec transplant, C1+C6: a per-finding "verdict" (fix / accept, confidence, exploitable / conditional / not exploitable) is cheap to add on top of 440 deterministic detectors and the existing graph, and it is what Wiz and Prowler now lead with.
- VectaSec transplant, C3: Conduktor has just defined the reference guardrail model for agents on brokers (four levels, creator-capped identity, traces, run-once preview). VectaSec can adopt the same ladder across all 39 connectors, not only Kafka; Conduktor is now a direct adjacent competitor on Kafka ACL hygiene and is giving it away.
- C8+C9: VectaSec's existing verify-after-fix rescan is on-trend; the 54% failure figure is strong marketing support for "we prove the fix".
- C10: "new advisory lands, we tell you in minutes which of your brokers/gateways/n8n instances are affected, with no rescan" is feasible from stored inventory and version data.
- C11: for a gateway product, a generated compensating control is a gateway policy/plugin snippet or broker ACL that neutralises a CVE until patching.

## 2. Autonomous / continuous pentesting and attack simulation; could safe "prove it is exploitable" apply to a broker or gateway?

### Takeaway
Autonomous pentesting is the best-funded frontier category of 2026 and the winning message is "exploitable, not just vulnerable", with a retest button. Buyer trust in AI-only testing fell sharply during the year, so the durable form is proof-backed validation with human-reviewable evidence, which maps well onto read-only checks against brokers and gateways.

### Inferences
- A broker/gateway "proof mode" does not need an LLM: for a finding such as "anonymous access enabled", VectaSec can perform one bounded, read-only action (list topics without credentials, fetch one message header, call an unauthenticated admin endpoint, enumerate an MCP server's tool list) and attach the transcript as evidence, turning a config finding into "exploitable: proven at 14:02". This is the Horizon3/Snyk/Prowler message applied deterministically, and avoids the false-positive problem that eroded trust in AI pentesting.
- The existing DNS ownership gate on the free exposure scan is the right consent mechanism to reuse for proof mode.
- C16 Tripwires transplant: after a finding, offer a decoy (canary topic/queue, canary API key in a gateway, canary n8n credential, decoy MCP tool) that alerts on touch. Acalvio shipped the same idea for agents (C36).

## 3. AI agent and MCP security as a category in late 2026

### Takeaway
Agent/MCP security became the most crowded category of 2026: every platform vendor shipped an agent registry, agent identity and an MCP gateway, and MCP itself went stateless with tighter OAuth in the 2026-07-28 spec. Analysts say governance (who authorised which agent to do what, with proof) is the lagging piece, and inventory/posture of MCP servers, skills and agent permissions is where an agentless scanner fits.

### Cited Findings
- **C24. MCP 2026-07-28 specification.** Released 2026-07-28 (RC locked 2026-05-21). Stateless core: `initialize` and `Mcp-Session-Id` retired (SEP-2575, SEP-2567); Streamable HTTP must carry `Mcp-Method` and `Mcp-Name` headers so gateways/WAFs can route and meter without parsing bodies (SEP-2243); `iss` validation per RFC 9207 closes an authorisation-server mix-up hole (SEP-2468); client credentials bound to issuer (SEP-2352); Dynamic Client Registration deprecated in favour of Client ID Metadata Documents; Roots, Sampling, Logging and legacy HTTP+SSE deprecated with a 12-month off-ramp (SEP-2577); extensions framework incl. Enterprise Managed Authorization. [P] — [MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- **C25. Agent registry with cross-platform sync and shadow-agent discovery (Microsoft Agent 365).** Ignite 2026-11-17. ### Inferences
- VectaSec already scans MCP servers and AI gateways. The 2026-07-28 spec creates an immediate, concrete detector pack: servers still on legacy HTTP+SSE or DCR, missing `iss` validation, still using deprecated Sampling/Roots, missing `Mcp-Method` headers. "MCP 2026-07-28 readiness report" is timely and cheap (C24).
- Toxic-flow analysis (C30) generalises beyond MCP: the same "read-sensitive + write-external" combination exists in an n8n/Zapier workflow, a gateway route chain, or a consumer that reads a PII topic and writes to a public webhook. VectaSec's graph can compute "toxic flows across the integration layer".
- "What breaks if I block this" (C25) is a blast-radius preview that VectaSec can show before any guided fix: which consumers, workflows and agents depend on the credential/ACL/MCP server being changed.
- Agent-permission map: join NHI inventory with agent registries (Entra Agent ID, Agent 365, Okta) to show "which AI agent can reach which topic/queue/API through which MCP tool and credential". Platform vendors inventory agents; none of the sources show them mapping agents to broker- or iPaaS-level permissions.
- Runtime blocking (C33) and identity issuance (C26) are crowded, enforcement-heavy and platform-owned; poor fit for a small agentless team.

### Gaps
- Noma, Lakera, Prompt Security, Operant, Pillar and Token Security: no dated 2026 product launches were retrieved (Operant's MCP Gateway dates to June 2025; Noma's last found round is July 2025).
- OpenAI and Google platform-level MCP admin controls were not researched in detail; Anthropic MCP-specific admin controls not found in sources.
- Entra Agent ID GA date not confirmed from a dated primary page; Okta "Agent SSO GA 2026-08-24" appears in one secondary source only.
- Docker MCP Catalog hardening post date unconfirmed; may be 2025.
